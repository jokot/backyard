Reference

Glossary

Every term introduced across lessons, kept current. Definitions are scoped to how the term is used in this project, not the broadest possible definition.

Multi-agent system (MAS)
Several autonomous AI agents that coordinate to get work done, instead of one general-purpose agent doing everything. The umbrella term for what this whole project is. Introduced in: Lesson 1
Context contamination
What happens when one AI assistant handles unrelated domains and irrelevant context from one leaks into another — e.g. tax details showing up while it's meant to be reviewing code. The core problem a multi-agent system is built to solve. Introduced in: Lesson 1 · coined in Zain Fathoni's Project Transformers
Specialist agent
An agent scoped to one narrow domain (e.g. "coding only"), with its own memory and personality, isolated from every other agent's context. Introduced in: Lesson 1
Coordinator agent
A router agent that decides which specialist should handle a given request, and holds cross-agent context the specialists don't need. In Zain's project this is "Optimus." Built in this project as Crazy Dave — a profile with no domain of its own, whose only job is creating a kanban task per request and subscribing the chat to it. Introduced in: Lesson 1 · built in Lesson 12
Hermes profile
Hermes Agent's unit of "a separate agent identity" — its own config file, default model/provider, skills, and memory, isolated from every other profile. This is the mechanism this project uses to build specialist agents: one profile per specialist. Introduced in: Lesson 1
Pooled credential
A stored login (API key or OAuth token) Hermes can hand to any profile that needs it, managed via hermes auth. Kept separate from profile config so the same credential can back several profiles' model choices. Introduced in: Lesson 2
Model tiering
Assigning cheaper or more capable models per agent based on what its role actually demands — a cross-domain coordinator gets the strongest model, a narrow specialist often doesn't need to. Zain Fathoni reported this cut his costs to roughly 15% of baseline. Introduced in: Lesson 2
Model aggregator (OpenRouter)
A service in front of many model providers behind one API key and one bill — one account reaches Anthropic, OpenAI, DeepSeek, Qwen, Zhipu/GLM, Moonshot/Kimi, MiniMax, and more. This project's chosen path for per-profile model choice, instead of a separate account per provider or reusing a personal subscription's login. Introduced in: Lesson 2
SOUL.md
A per-profile system prompt: who the agent is, what domain it owns, what it explicitly does not own (redirect rather than attempt), and its tone. The boundary clause is what actually stops scope creep back toward "one assistant that does everything" — not just the domain description. Introduced in: Lesson 3
Prompt dilution
When a project-specific instruction (like a SOUL.md clause) is a small fraction of a much larger system prompt, and gets softened or ignored as a result. Diagnosed with hermes prompt-size --json, which reports the full prompt breakdown without an API call. The fix is not a longer prompt — it's a harder-worded clause with no soft middle ground. Introduced in: Lesson 3
MEMORY.md
A per-profile file where Hermes records durable agent notes — conventions, decisions, recurring facts — read into every new session automatically. Lives at ~/.hermes/profiles/<profile>/memories/MEMORY.md (the memories/ subfolder is easy to miss). Copied wholesale by --clone-from, so a cloned profile inherits the source profile's memory, not a blank slate. Introduced in: Lesson 4
USER.md
A per-profile file holding facts specifically about the user, separate from MEMORY.md's agent/project notes. Same location and clone behavior as MEMORY.md. Introduced in: Lesson 4
Gateway
Hermes's messaging bridge subsystem: connects a profile to chat platforms (Telegram, Discord, WhatsApp, Slack, Signal). Messages sent there reach the profile's agent loop directly — same SOUL.md, same memory, same model as a terminal session. Introduced in: Lesson 5
Hermes skill
A folder with a SKILL.md file (name, description, and instructions) that a profile can load and follow. Same format as a Claude Code skill, so a folder can be copied straight from one system into ~/.hermes/profiles/<profile>/skills/ and Hermes picks it up with no extra step. Skills live under a profile, not globally — copying one into Sunflower's folder does not make Peashooter see it too. Introduced in: Lesson 9
Profile description
A one- or two-sentence field on each Hermes profile (profile.yaml's description, set or read with hermes profile describe <name> [--text "..."]). It is the only signal hermes kanban decompose sees when choosing which profile to route a task to — not SOUL.md, not memory, not skills. A profile with no description still appears in the routing prompt, tagged ⚠ undescribed, and the LLM falls back to matching on the profile's name alone. Introduced in: Lesson 10
Shared skill store
~/.agents/skills/ — a personal skill folder shared across this machine's agent tools, tracked by its own ~/.agents/skills/.skill-lock.json. Every entry in ~/.claude/skills/ is a symlink into it, not a real folder. Copying a skill with cp -R, source it from here directly — copying the ~/.claude/skills/ alias instead copies the symlink itself (macOS cp -R default behavior), producing a broken link once it's moved somewhere the original relative path no longer resolves from. Introduced in: Lesson 9
Bundled skill manifest
A .bundled_manifest file inside every profile's skills/ folder, one line per bundled skill as name:hash. hermes update reads it to decide what to sync — a skill whose folder is missing but still listed here is read as a deliberate deletion, not damage, and is never recopied. This is what makes deleting an unwanted bundled skill's folder a safe, permanent choice instead of a fragile hand-typed skills.disabled list. Reversible with hermes skills reset <name> --restore, which recopies one skill from Hermes's own bundled source. Introduced in: Lesson 9
Kanban board
A single SQLite file, shared across every Hermes profile on the machine — one board, not one per profile. A task moves through five columns: triage → todo → ready → running → done. Managed with hermes kanban init, hermes kanban boards, and the rest of the hermes kanban subcommands. Introduced in: Lesson 15
Decompose
hermes kanban decompose — reads every profile's description (the routing signal from Lesson 10) and fans a raw task into one or more children, each with an explicit assignee=. Turns a task Crazy Dave filed into work a specialist can actually pick up. Introduced in: Lesson 15
Orchestrator profile
The kanban.orchestrator_profile key in every profile's config.yaml, empty by default. Set to 'crazydave' in all three profiles so any profile's gateway — whichever one holds the dispatcher lock at ~/.hermes/kanban/.dispatcher.lock — knows which profile's requests are routing instructions, not direct work. Introduced in: Lesson 15
Forum topic
A named sub-thread inside a Telegram supergroup. Telegram gives each topic a numeric message_thread_id and stamps it on every message posted there. Telegram omits the id for the General topic, and Hermes normalizes that absence to thread 1 (adapter.py:583). The numbers are not shown in the Telegram app — read them from the address bar in Telegram Web. Introduced in: Lesson 18
Group privacy (Telegram)
A per-bot Telegram setting, enabled by default, that delivers only messages naming the bot, replying to it, or starting with a command. Applied above Hermes, so an enabled setting produces silence with no log entry and no error. Turned off through BotFather. Introduced in: Lesson 18
Mention gating
The require_mention key, which keeps a profile silent in a group until a message names it. Applies to group chats only, never to private chats. Its companion exclusive_bot_mentions, on by default, makes a mention exclusive: only the named bot processes the message. Introduced in: Lesson 19
Free-response topic
One entry of the form <chat_id>:<thread_id> in free_response_topics, making a profile answer unnamed messages in exactly one topic. Checked before require_mention, so one topic opens without opening the group. Undocumented — it exists only in the adapter source at adapter.py:7251. Contrast ignored_threads, which is checked before every other gate and therefore blocks mentions too. Introduced in: Lesson 19
Session history precedent
A model follows the pattern of its own visible conversation history instead of a rule in the system prompt that contradicts it. A gateway restart rebuilds the prompt and keeps the history, so a SOUL.md change can appear to do nothing. Send /new in every chat the profile listens to. Introduced in: Lesson 20
Silent non-routing
A coordinator answers a work request conversationally instead of filing it, so no task exists and no record of the request survives. It is the failure a junk task is traded against. A junk task is visible on the board and one command removes it, so Crazy Dave keeps filing as the default and replies only in named moments. Introduced in: Lesson 20
One-way mirror
A copy of state that a second system displays but never feeds back. Fizzy holds one card per root kanban task, written by Crazy Dave and read by no agent. A drifted mirror shows a stale view rather than causing a wrong action, which is the whole reason the direction is enforced. Introduced in: Lesson 22
Pipe
A fixed buffer in memory with a writer at one end and a reader at the other. An agent gives every command it starts a pipe, so that the agent can read the output. A write to a full pipe does not fail and does not return. It blocks until a reader takes bytes out, so a pipe that lost its reader stops the writer forever. This machine gives a pipe 16,384 bytes and grows it to 65,536 bytes under load. Introduced in: Lesson 31
Orphan process
A process whose parent has exited. A parent process id of 1 names one, because the operating system adopts a process that loses its parent. Every service an agent starts becomes an orphan, since the agent exits within a turn. An orphan that still holds the pipes of its parent is the failure of learning record 0038. Introduced in: Lesson 31
Session prompt
The system prompt that the gateway builds once for a session and then stores in the sessions table. Later turns reuse the stored text verbatim, so an edit of SOUL.md reaches an open session only after /new. A dispatched kanban worker gets a new session for each task, so it reads the file as it stands. Introduced in: Lesson 31
Dependency edge
The relation the kanban words parents and children name. A parent must reach done before its child starts, so a child waits on every parent. A root task waits on every one of its workers, so the root task lists its workers as parents. A worker therefore reaches its own root task through children, never through parents. Introduced in: Lesson 32
Watchdog
A scheduled job that checks a fixed set of rules. It prints nothing when every rule holds. Silence is the pass result, so a delivered message always names a real defect. Built as roster-audit.sh, the first scheduled job in this project. Introduced in: Lesson 34
WAL sidecar file
One of two files, -shm and -wal, that SQLite keeps beside a database file running in WAL mode. Both files exist only while a process holds the database open. A connection opened -readonly holds no permission to create the files it needs, so SQLite refuses to open the database until they already exist. Introduced in: Lesson 35
