Reference

Glossary

Every term introduced across lessons, kept current. Definitions are scoped to how the term is used in this project, not the broadest possible definition.

Multi-agent system (MAS)
Several autonomous AI agents that coordinate to get work done, instead of one general-purpose agent doing everything. The umbrella term for what this whole project is. Introduced in: Lesson 1
Context contamination
What happens when one AI assistant handles unrelated domains and irrelevant context from one leaks into another — e.g. tax details showing up while it's meant to be reviewing code. The core problem a multi-agent system is built to solve. Introduced in: Lesson 1 · coined in Zain Fathoni's Project Transformers
Specialist agent
An agent scoped to one narrow domain (e.g. "coding only"), with its own memory and personality, isolated from every other agent's context. Introduced in: Lesson 1
Coordinator agent
A router agent that decides which specialist should handle a given request, and holds cross-agent context the specialists don't need. In Zain's project this is "Optimus." Not built yet in this project — see Stage 2 of the build spec. Introduced in: Lesson 1
Hermes profile
Hermes Agent's unit of "a separate agent identity" — its own config file, default model/provider, skills, and memory, isolated from every other profile. This is the mechanism this project uses to build specialist agents: one profile per specialist. Introduced in: Lesson 1
Pooled credential
A stored login (API key or OAuth token) Hermes can hand to any profile that needs it, managed via hermes auth. Kept separate from profile config so the same credential can back several profiles' model choices. Introduced in: Lesson 2
Model tiering
Assigning cheaper or more capable models per agent based on what its role actually demands — a cross-domain coordinator gets the strongest model, a narrow specialist often doesn't need to. Zain Fathoni reported this cut his costs to roughly 15% of baseline. Introduced in: Lesson 2
Model aggregator (OpenRouter)
A service in front of many model providers behind one API key and one bill — one account reaches Anthropic, OpenAI, DeepSeek, Qwen, Zhipu/GLM, Moonshot/Kimi, MiniMax, and more. This project's chosen path for per-profile model choice, instead of a separate account per provider or reusing a personal subscription's login. Introduced in: Lesson 2
SOUL.md
A per-profile system prompt: who the agent is, what domain it owns, what it explicitly does not own (redirect rather than attempt), and its tone. The boundary clause is what actually stops scope creep back toward "one assistant that does everything" — not just the domain description. Introduced in: Lesson 3

Terms get added here as lessons introduce them: SOUL.md, MEMORY.md/USER.md, gateway, and kanban are coming in later lessons.
