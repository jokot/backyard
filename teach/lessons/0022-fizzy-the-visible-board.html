Lesson 22 of the Stage 3 build

A board you can read on a phone

The Hermes kanban board is a SQLite file behind a command line interface. It works, and you cannot glance at it from a train. This lesson adds Fizzy as a second, readable view — and draws a hard line around what that view is allowed to do.

A mirror, not a second brain

Knowledge

Fizzy will hold a copy of every root task. That copy is a one-way mirror: written by Crazy Dave, read by you, and never read back by any agent. The Hermes board stays the only source of truth for routing and for task state.

That constraint is the entire safety argument. A two-way integration has a failure mode where the two boards disagree and an agent acts on the wrong one. A one-way mirror has a failure mode where the display is stale. Stale is a nuisance. Wrong is a bug you chase for a day.

Lesson 17 recorded Zain Fathoni's version of the same lesson from the other side: he built a homebrew task abstraction called "beads", found it unreliable, and replaced it with a real task system. Our real task system is already the Hermes board. Fizzy is the window on it, not a competitor to it.

What the spike found

Knowledge

Fizzy is 37signals' kanban tracker. Two findings shaped this lesson.

There is an official command line interface. basecamp/fizzy-cli is Go, MIT-licensed, and ships an agent skill plus a read-only MCP server. That matters because it makes the integration the same shape as hermes send from Lesson 17: an agent already holds the terminal tool, so a command line interface needs no new plumbing at all.

Two of the reference project's helper tools are now obsolete. Zain wrote fizzy-md because "Fizzy's API expects HTML, but agents naturally write Markdown" — and the official skill now states that rich text fields accept Markdown or HTML. He also wrote fizzy-create-card.sh, which the official tool replaces. Copying a reference architecture is not the same as copying its workarounds. Check which of them the ecosystem has since absorbed.

One limit is worth knowing before you rely on Fizzy for anything else: a Fizzy webhook payload carries a card's title and url and no description body. Any push integration would have to fetch the card to learn what it says. This stage sends no webhooks, so it does not pay that cost.

Do this now

Skill — hands on

1. Count the cost before you start. The hosted free tier allows 1,000 cards. Reports state that a deleted card still counts against that limit, so every test card you make is spent permanently. The paid tier is 20 US dollars per month. Self-hosting through Docker or Kamal is free and is its own project, deliberately out of scope here.

2. Install the command line interface.

brew install --cask basecamp/tap/fizzy
fizzy --version

If you have the old 3.x formula from the robzolkos/fizzy-cli tap, unlink it first. A cask will not overwrite a bin/fizzy symlink that a formula owns, and installing over it silently skips the binary:

brew tap basecamp/tap
brew unlink fizzy-cli
brew install --cask basecamp/tap/fizzy
brew uninstall --formula --force fizzy-cli
brew untap robzolkos/fizzy-cli

3. Create the account, one board, and a token. Sign up at fizzy.do. Create a single board named plants. Create a personal access token in the account settings.

4. Authenticate as a named profile. Crazy Dave is the only agent that will ever call this tool, so give the profile its name:

fizzy auth login "$FIZZY_TOKEN" --profile crazydave
fizzy auth status

If the command asks for an account, take the id from the same settings page and add --account <id>.

5. Read the board id.

fizzy board list --profile crazydave

The output is JSON. The --jq flag is built into the tool, so no external jq is needed:

fizzy board list --profile crazydave --jq '.data[0].id'

Write that id down. Lesson 23 puts it into Crazy Dave's SOUL.md.

6. Create one probe card and read the output carefully. This step exists to learn something the repository does not document: which field of the returned JSON later commands accept as a card address.

fizzy card create --profile crazydave --board <BOARD_ID> \
  --title "probe: which field addresses a card" \
  --description "Created to learn the card address field."

Read the JSON. Then confirm your reading with the two commands Lesson 23 actually uses:

fizzy comment create --profile crazydave --card <VALUE> --body "probe comment"
fizzy card close --help

The second command tells you whether fizzy card close takes the card as a positional argument or as a flag. Record the real form. Do not carry a guess into a SOUL.md.

7. Close the probe card using the form you just confirmed, and check on the Fizzy web interface that it is closed and carries your comment. That is the full write path Crazy Dave will use.

Why is Crazy Dave forbidden from ever reading a Fizzy card?

Right. Once an agent reads Fizzy to decide something, the two boards can disagree and the agent can act on the wrong one. Write-only keeps every failure to the display.

Reading is fully supported — fizzy card list and the MCP server both do it. The ban is a design decision, not a limitation.

That limit is real and worth knowing, but it applies to webhook payloads. A direct card read returns the full card.
