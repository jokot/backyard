Lesson 22 of the Stage 3 build

A board you can read on a phone

The Hermes kanban board is a SQLite file behind a command line interface. It works, and you cannot glance at it from a train. This lesson adds Fizzy as a second, readable view — and draws a hard line around what that view is allowed to do.

A mirror, not a second brain

Knowledge

Fizzy will hold a copy of every root task. That copy is a one-way mirror: written by Crazy Dave, read by you, and never read back by any agent. The Hermes board stays the only source of truth for routing and for task state.

That constraint is the entire safety argument. A two-way integration has a failure mode where the two boards disagree and an agent acts on the wrong one. A one-way mirror has a failure mode where the display is stale. Stale is a nuisance. Wrong is a bug you chase for a day.

Lesson 17 recorded Zain Fathoni's version of the same lesson from the other side: he built a homebrew task abstraction called "beads", found it unreliable, and replaced it with a real task system. Our real task system is already the Hermes board. Fizzy is the window on it, not a competitor to it.

What the spike found

Knowledge

Fizzy is 37signals' kanban tracker. Two findings shaped this lesson.

There is an official command line interface. basecamp/fizzy-cli is Go, MIT-licensed, and ships an agent skill plus a read-only MCP server. That matters because it makes the integration the same shape as hermes send from Lesson 17: an agent already holds the terminal tool, so a command line interface needs no new plumbing at all.

Two of the reference project's helper tools are now obsolete. Zain wrote fizzy-md because "Fizzy's API expects HTML, but agents naturally write Markdown" — and the official skill now states that rich text fields accept Markdown or HTML. He also wrote fizzy-create-card.sh, which the official tool replaces. Copying a reference architecture is not the same as copying its workarounds. Check which of them the ecosystem has since absorbed.

One limit is worth knowing before you rely on Fizzy for anything else: a Fizzy webhook payload carries a card's title and url and no description body. Any push integration would have to fetch the card to learn what it says. This stage sends no webhooks, so it does not pay that cost.

Do this now

Skill — hands on

1. Count the cost before you start. The hosted free tier allows 1,000 cards. Reports state that a deleted card still counts against that limit, so every test card you make is spent permanently. The paid tier is 20 US dollars per month. Self-hosting through Docker or Kamal is free and is its own project, deliberately out of scope here.

2. Install the command line interface.

brew install --cask basecamp/tap/fizzy
fizzy --version

Expect fizzy version 4.0.1 or later. Run this check before you read the next paragraph:

which fizzy | xargs ls -l

A link into Caskroom/fizzy/ means the cask owns the binary and you are finished. Skip the rest of this step.

A link into Cellar/fizzy-cli/ means the old 3.x formula from the robzolkos/fizzy-cli tap owns it. Unlink that formula first. A cask will not overwrite a bin/fizzy symlink that a formula owns, and the install then skips the binary without an error:

brew tap basecamp/tap
brew unlink fizzy-cli
brew install --cask basecamp/tap/fizzy
brew uninstall --formula --force fizzy-cli
brew untap robzolkos/fizzy-cli

3. Create the account, one board, and a token. Register at fizzy.do. Create one board and name it Backyard. Step 5 selects the board by that name, so a different name means a different selector. Create a personal access token in the account settings.

4. Authenticate as a named profile, and pass the account yourself. A profile is a local set of credentials. An account is the Fizzy organisation those credentials belong to. The two are different, and --account is not optional. Read the account first:

fizzy identity show --jq '.data.accounts[0].slug | ltrimstr("/")'

That prints digits, for example 6280439. The --jq flag is necessary here. Plain fizzy identity show prints accounts: [1 items] and hides every field inside the array. The raw slug value carries a leading slash, because the field is a URL path fragment, and ltrimstr("/") removes it. The id field of the same account works too:

fizzy auth login "$FIZZY_TOKEN" --profile crazydave --account <slug>
fizzy auth status

Read the account value in that output. It must be the slug. If it is the word crazydave, read the correction below before you continue.

5. Read the board id, and select it by name.

fizzy board list --profile crazydave

Expect two boards, not one. Fizzy creates a board named Playground with every new account, and it sorts first. Never address a board by position for that reason. The --jq flag is built into the tool, so no external jq is needed:

fizzy board list --profile crazydave --jq '.data[] | select(.name=="Backyard") | .id'

The output is one 25 character id, for example 03gu8u5gami98obpx1fvtgzd8. A selector such as .data[0].id reads correctly and returns the Playground id, which would send every mirrored card to the demo board.

Write that id down. Lesson 23 puts it into Crazy Dave's SOUL.md.

6. Create one probe card and read the output carefully. This step exists to learn something the repository does not document: which field of the returned JSON later commands accept as a card address.

fizzy card create --profile crazydave --board <BOARD_ID> \
  --title "probe: which field addresses a card" \
  --description "Created to learn the card address field."

Read the JSON. One card carries two addresses, and they are not interchangeable:

{"id":"03gu90tjii5haspil51dhkvbo","number":12,
 "title":"probe: which field addresses a card",
 "url":"https://app.fizzy.do/6280439/cards/12"}

Ask the tool which one to use, rather than guessing:

fizzy comment create --help
fizzy card close --help

The answers are exact, and they disagree in shape:

comment create   --card <CARD>   Card number (required)
card close       USAGE: fizzy card close CARD_NUMBER

So both commands take number, and neither takes id. One takes it as a flag and one takes it as a positional argument. Note the whole rule before you continue: a board is addressed by its 25 character id, and a card is addressed by its short number. One tool, two addressing schemes.

7. Comment on the probe card, then close it. Substitute your own card number:

fizzy comment create --profile crazydave --card 12 --body "probe comment"
fizzy card close 12 --profile crazydave

Check on the Fizzy web interface that the card is closed and carries the comment. That is the full write path Crazy Dave will use.

Correction — a profile is not an account

The first version of step 4 treated --account as optional. The login then stored the profile name as the account, and the next command failed:

fizzy board list --profile crazydave
Resource not found: https://app.fizzy.do/crazydave/boards.json

Read the URL. Fizzy addresses every resource as https://app.fizzy.do/<account>/…, so the client asked for an account named crazydave. No such account exists. The real account carries a numeric slug such as 6280439, and fizzy identity show prints it.

Two repair paths do not work here, and the reason is precedence. FIZZY_ACCOUNT answers with Warning: FIZZY_ACCOUNT is deprecated and changes nothing. A local .fizzy.yaml file changes nothing either. fizzy config explain shows why: the winning candidate is source: profile crazydave, and the profile beats the flag, the environment, the local file and the global file. The account is stored beside the token, so only a second login rewrites it:

fizzy auth login "$FIZZY_TOKEN" --profile crazydave --account 6280439
fizzy auth status

One more file holds the same wrong value. ~/.config/fizzy/config.yaml carries account: crazydave from the same mistake. The profile overrides it, so it causes no failure, and it will still mislead you during the next problem. Correct it or delete the line.

The general shape: the word profile means a different thing in every tool that uses it. In Hermes it selects an agent. In Fizzy it selects a set of saved credentials. Neither meaning implies the other, and a name that reads correctly in both tools is the easiest kind of mistake to miss.

Why is Crazy Dave forbidden from ever reading a Fizzy card?

Right. Once an agent reads Fizzy to decide something, the two boards can disagree and the agent can act on the wrong one. Write-only keeps every failure to the display.

Reading is fully supported — fizzy card list and the MCP server both do it. The ban is a design decision, not a limitation.

That limit is real and worth knowing, but it applies to webhook payloads. A direct card read returns the full card.
