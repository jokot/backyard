Lesson 29 of the Stage 4 build

Five headings you can edit without restarting anything

Torchwood has an identity, a room, and a rule that says to read TEMPLATE.md. The file does not exist, so every interview stops at one sentence. This lesson writes the file, runs four tests on the finished bot, and shows that one heading added by hand changes the next prompt with no edit to SOUL.md.

The contract

Knowledge

The template is the skeleton of the output. It is not a description of the skeleton, and it is not an example of one. Each ## heading in the file becomes a ## heading in the finished prompt, in file order. To add a section, add a heading. To remove a section, delete the heading.

Nothing in Hermes reads this file. A search of ~/.hermes/hermes-agent/hermes_cli/ for the string TEMPLATE.md returns no match. Hermes loads SOUL.md, MEMORY.md, and USER.md into the prompt. It knows nothing about this file.

That is the whole reason the edit is cheap. The agent reads the file with a read command at the start of each interview, so a new heading reaches the next prompt. No restart, no reload, no setting. Test 2 measures exactly this.

Why two of the five headings exist

Knowledge

A reader who knows why a heading exists keeps the heading. Two of the five were bought with real failures in this project.

Deliverable comes from learning record 0018. A task named no durable destination, so the worker built the artifact inside a scratch workspace. The report gave a path. The path stopped existing. The heading forces one real path, chosen before the work starts.

Done when comes from learning record 0016, where a specification passed review carrying tests_run: 0. A check the worker can run without asking a question is the only kind that closes a task honestly. One checkbox for each check.

The other three carry their weight in one line each. Goal states the outcome and not the method. Context gives every path, and the path has to survive the Checked: rule from Lesson 28. Constraints states what the worker must not do, and it leaves the prompt when the interview finds nothing for it.

Do this now

Skill — hands on

1. Create the file at ~/.hermes/profiles/torchwood/TEMPLATE.md with this content:

# Prompt template

Torchwood reads this file at the start of every interview.
Each heading below becomes a heading in the finished prompt.

## Goal
One sentence. State the outcome, not the method.

## Context
What exists now. Give every path. Confirm each path with a command.

## Constraints
What the worker must not do. Omit this section when the interview
finds nothing for it.

## Deliverable
The exact path that must hold the artifact when the work is done.
Never a scratch directory.

## Done when
Checks the worker can run without asking a question. One checkbox
for each check.

2. Check the heading count.

grep -c '^## ' ~/.hermes/profiles/torchwood/TEMPLATE.md

Expected: 5. The line # Prompt template carries one hash, so it does not count.

3. Do not restart the gateway. Nothing in the running process holds this file. If an interview picks the file up without a restart, the contract above is true. If a restart turns out to be necessary, that is a real finding and it earns a record.

The shape of a finished prompt

Knowledge — worked example

This example was built by running the two commands in its own trailer. The first draft of it cited line 12 of the script and a bug that no longer exists, and the commands caught that.

## Goal
Make the Zuma start script survive a move of the repository.

## Context
projects/zuma/start_servers.sh line 3 holds the absolute path
/Users/jokot/dev/plants/projects/zuma. The script fails after any move.
The directory holds start_servers.sh, check_public.py, index.html,
and logs.

## Deliverable
projects/zuma/start_servers.sh

## Done when
- [ ] grep -c '/Users/jokot' projects/zuma/start_servers.sh prints 0
- [ ] bash projects/zuma/start_servers.sh prints one web_pid and one ngrok_pid

Checked:
- sed -n '3p' projects/zuma/start_servers.sh
- ls projects/zuma/

The example holds no Constraints heading, because the interview found nothing for it. Every path above the trailer traces to one of the two commands in the trailer. That is the rule from Lesson 28, doing its work.

Skill — test 1, a real interview

Post this in the Prompts topic:

I want a prompt for adding a pause key to projects/tetris

The task names code that exists on this machine. projects/tetris/ holds game.js, index.html, style.css, test.js, and SPEC.md, so every question has an answer a read command can reach. Read the next box for the reason that matters.

Expected shape of the run. Torchwood asks one question for each message, and each question names a section. Torchwood runs read commands rather than asking you for a path. Torchwood then sends one message that holds one fenced block.

Run these four checks by eye on that block:

  1. The message count is one, and the fenced block count is one.
  2. The headings match TEMPLATE.md in file order. The Constraints heading may be absent when the interview found nothing for it.
  3. A Checked: trailer closes the block and lists at least one command.
  4. Every path above the trailer traces to a listed command.
Why the first version of this test failed

Test 1 first read I want to add a --description flag to fizzy card create. Torchwood answered with a question: Context — which repository contains the fizzy CLI?

The question is correct, and the task is the defect. fizzy resolves to /opt/homebrew/bin/fizzy, which links to /opt/homebrew/Caskroom/fizzy/4.0.1/fizzy. The binary comes from a Homebrew cask, and no fizzy source lives on this machine. A prompt for that task cannot name a Deliverable path, because no file here holds the code to change.

Keep the rule. An interview ends in a prompt only when the work has a destination. A task whose code is absent produces a question, and the question is the honest output. Record 0029 holds the full reply, including a second defect it exposed.

Skill — test 2, a durable template edit

Add this heading to TEMPLATE.md, after ## Constraints:

## Rollback
How to undo the change in one command, when an undo is possible.

Run a second interview on any small task. Expected: the new prompt holds a ## Rollback heading in that position.

Delete the heading. Run a third interview. Expected: the heading is gone.

State what this proves. A file you edited by hand changed the output, with no change to SOUL.md and no gateway restart. That is the whole reason the skeleton lives in its own file.

Skill — test 3, a per-prompt override

Post this in the topic:

What test 4 does not prove

Test 4 measures the behaviour of one run. It does not prove that a write cannot happen. The read-only rule is prose, and Lesson 28 shows that the toolset and the terminal of Torchwood match Peashooter exactly. Record 0015 states the rule this breaks: set the limits from the implementation, not from the conversation.

Stage 5 closes the gap with a probe of terminal.backend, because Magnet-shroom moves and deletes files. Nobody has run that probe. Record the result of test 4 as the behaviour of one run, and write nothing stronger.

You add a ## Rollback heading to TEMPLATE.md. What has to happen before the next prompt carries it?

Right. Hermes never loads this file, so no cached copy exists to refresh. The read command runs inside the interview.

True of SOUL.md, which Hermes loads into the prompt. A search of the source for TEMPLATE.md returns no match at all.

The soul file names the file and the ordering rule. It lists no heading, which is what makes a template edit cheap.

Right. The rule is prose, so the evidence is one sample of behaviour and never a boundary.

Record 0015 rejects that step. A limit drawn from wording is a request, and the terminal here is the one Peashooter writes with.

A refusal needs no mechanism at all. The model read a sentence and followed it, exactly as it followed the missing-file sentence.
