Lesson 9 of the Stage 2 build

Only the skills each specialist needs

Sunflower's SOUL.md sets the boundary in words. This lesson sets it in tools too — giving Sunflower two skills from Claude Code's superpowers plugin, then deleting the skill folders neither Sunflower nor Peashooter actually uses, so each profile's ls matches its own domain.

A correction, made in front of you

Correction — I was wrong about this, and checked before saying so again

Asked earlier whether a Claude Code skill like superpowers:brainstorming could be given to a Hermes profile, I said no confirmed path existed. That was wrong — I had only checked hermes skills install, which needs a URL or registry name, and stopped there.

Peashooter's own bot had already done it, by a plainer route: a Hermes skill and a Claude Code skill are the same format, a folder with a SKILL.md file. Copying the folder straight into a profile's skills/ directory works — no install command needed. I diffed the copies against the real source myself before trusting the claim:

diff ~/.hermes/profiles/peashooter/skills/brainstorming/SKILL.md \
     /Users/jokot/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/brainstorming/SKILL.md
# → identical

diff ~/.hermes/profiles/peashooter/skills/teach/SKILL.md \
     ~/.claude/skills/teach/SKILL.md
# → identical

Both were byte-for-byte the real thing, and neither existed in Sunflower's skill folder or the shared default profile — confirming skills are scoped per profile, exactly like memory and SOUL.md.

What Sunflower is getting, and why

Knowledge

Hermes skill — a folder with a SKILL.md (name, description, instructions) that a profile can load and follow. Copy the folder into ~/.hermes/profiles/<profile>/skills/ and Hermes picks it up with no extra step, no reload command needed.

Two skills fit Sunflower's domain from the official superpowers plugin: brainstorming (the dialogue this whole project has been built through) and writing-plans (the format this project's own implementation plans follow). The other twelve skills in that plugin are code, git, or review skills — Peashooter's domain, not Sunflower's.

Skill — hands on

cp -R /Users/jokot/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/brainstorming ~/.hermes/profiles/sunflower/skills/
cp -R /Users/jokot/.claude/plugins/cache/claude-plugins-official/superpowers/6.3.0/skills/writing-plans ~/.hermes/profiles/sunflower/skills/

  2. devops/kanban-worker documents the pitfalls a profile hits once Hermes dispatches it a kanban task. Both Sunflower and Peashooter become workers once Lesson 14 initializes the board, so both keep it, ahead of needing it.

Why delete, instead of turning skills off in config

Correction — this lesson changed method after a real bug

The first version of this lesson kept every unwanted skill installed and turned it off with a skills.disabled list in each profile's config.yaml — a plain list under skills:, read from hermes_cli/skills_config.py. It worked, but it also hid a hand-typed list of over eighty names that had to stay perfectly correct.

It did not stay correct. When you ran it, Sunflower showed 12 skills enabled instead of five, and Peashooter showed 26 instead of twenty. Two mistakes caused it: the inventory scan that built the list used find ... -maxdepth 3, which missed six skills nested one level deeper under mlops/{evaluation,inference,models}/; and two names — spike for Sunflower, yuanbao for Peashooter — were dropped by hand while copying one profile's list into the other's.

Patching the list a second time would only move the risk of a third bug further down the road. Deleting the unwanted skill folders removes the list entirely — there is nothing left to keep in sync by hand.

Knowledge

Every profile's skills/ folder carries a .bundled_manifest file: one line per bundled skill, name:hash, written by Hermes's own sync tool (tools/skills_sync.py). hermes update reads this file and re-copies any bundled skill whose folder is missing — unless the manifest already lists that skill. The exact branch, read straight from the source:

# In manifest but not on disk — user deleted it
skipped += 1

A skill that is in the manifest but missing from disk is read as a deliberate removal, not damage to repair. hermes update leaves it deleted, this run and every run after. Deleting a skill folder is as reversible as disabling one, just through a different door: hermes skills reset <name> --restore copies that one skill back from Hermes's own bundled source, no plugin path or backup file needed.

Its absence here is expected, not a sixth skill to chase down.

Why is it safe to permanently delete a bundled skill's folder instead of listing it under skills.disabled?

Right — confirmed by reading tools/skills_sync.py directly: a skill in the manifest but absent on disk is skipped, not recopied, on every future hermes update.

No automatic backup exists — the way back is hermes skills reset <name> --restore, which re-copies the skill from Hermes's bundled source on request.

It does work — the problem this lesson ran into wasn't the mechanism, it was an 80-plus-line list that was hard to keep correct by hand.
