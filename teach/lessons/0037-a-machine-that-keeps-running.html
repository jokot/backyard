Lesson 37 · Stage 6 build

Prepare the server, and keep the services alive after you disconnect

This lesson prepares the server before the move of any bot. You run every command yourself, because each command changes the server. Nothing stops on the Mac. All four bots continue to answer Telegram while you work. Lesson 31 taught the same subject on the Mac, where launchd holds the service. Linux gives a different answer. The difference can stop four bots at the same time.

The word SERVER is a placeholder

Knowledge

The commands in this lesson show the word SERVER. The word SERVER is a placeholder. Replace the word SERVER with the IPv4 address of your VPS each time that you type a command.

An example makes the rule concrete. The IPv4 address 51.79.200.14 gives this command:

ssh ubuntu@51.79.200.14

The same rule applies to PASTE-THE-KEY-LINE-HERE in the section about the SSH key. Both words are placeholders, and neither word works as typed.

Where each command runs

Knowledge

One command in this lesson runs on the Mac. That command is the ssh that opens a session on the server. Every other command runs inside that session, on the server.

Most commands in this lesson start with sudo. The ubuntu account needs sudo. The root account does not. Remove the word sudo from each command when you connect as root.

The two curl commands measure the route from Singapore to Telegram, and the route from Singapore to Anthropic. A curl command on the Mac measures your home connection instead. The home number decides nothing.

Reach the server, step by step

Skill — hands on

Do these seven steps in order, in a terminal on the Mac:

  1. Find the address. Open the OVHcloud control panel at www.ovh.com/manager. Select Bare Metal Cloud → Virtual Private Servers, then select your VPS. The summary page shows a field with the name IPv4. Record that address.
  2. Find the account name. OVHcloud sends one mail with the subject Your VPS is ready. The account is ubuntu when you gave an SSH key at order time. The account is root when you did not. The mail holds the password for the root account.
  3. Open the first session. Run one of these two commands. Use the account from step 2: 
    ssh ubuntu@SERVER
ssh root@SERVER
  4. Accept the host key. The first connection prints a fingerprint and asks a question: 
    The authenticity of host 'SERVER' can't be established.
ED25519 key fingerprint is SHA256:…
Are you sure you want to continue connecting (yes/no/[fingerprint])?
    Type yes and press Return. SSH writes the key into ~/.ssh/known_hosts. SSH does not ask the question again for this server. A single letter y does not answer the question, because SSH reads the full word.
  5. Change the password of the root account. Do this step only when the mail gave you a password. Ubuntu asks for the old password, then for a new password two times. Save the new password in your password manager. No later step can recover a lost password.
  6. Confirm the machine. Run these two commands: 
    hostname -I
lsb_release -d
    The first command prints your own IPv4 address. The second command prints a line that names Ubuntu 24.04. A different version means that the order used the wrong image. Stop at this step and report the version.
  7. Keep the session open. Every later command in this lesson runs in this session. A later section adds your Mac key to the server. You test that key from a second terminal, and the first session stays open during the test.

CAUTION: Do not close the last session before the test of the SSH key succeeds. A wrong permission on authorized_keys locks you out of the server. The recovery path is Rescue mode in the OVHcloud panel, and it costs one reboot and about 20 minutes.

A user service stops when the last session closes

Knowledge

Hermes installs its systemd unit in user scope by default. Line 1184 of gateway.py holds the line that decides the scope:

systemctl_prefix = "systemctl " if system else "systemctl --user "

System scope is the other option. Line 1813 writes the unit into /etc/systemd/system. Line 1829 states that system scope needs root.

User scope avoids root, and user scope carries one condition. Linux stops a unit in user scope when the last session of that user closes. You start four bots over SSH, then you close the terminal. All four bots stop. The server continues to run, and the roster goes silent.

Linger removes that condition. Linger keeps a user manager alive with no open session.

Hermes already knows this condition

Hermes does not wait for you to find the trap. Line 1955 of gateway.py runs the command itself:

["loginctl", "enable-linger", username],

The docstring at line 1922 states the condition. The command works without root when polkit permits the command. When polkit denies the command, lines 1965, 1987 and 1996 give the same fix: sudo loginctl enable-linger <user>.

One question stays open. Why run the command by hand? Hermes runs the automatic attempt during gateway install in Task 3. A denied attempt stops that install, and you then debug two problems at the same time. The manual command removes that failure path. The command changes nothing when linger is already active.

Make the user, and keep its services alive

Skill — hands on 
sudo adduser --disabled-password --gecos "" hermes
sudo loginctl enable-linger hermes
loginctl show-user hermes | grep Linger

The third command prints Linger=yes. That one line is the whole proof. When the line reads Linger=no, stop and report the line. Every later task depends on the value yes.

The hermes account takes no password. You reach the account with sudo -u hermes -i from your own account. Rsync reaches the account over SSH.

Give the hermes account your Mac key

Knowledge

Task 5 copies 109 MB over rsync during a live window. All four bots stay down during that window. A password prompt in the middle of the window costs time. An SSH key removes the prompt.

The hermes account must exist before this section. The previous section makes the account. A chown against an absent account fails with the message chown: invalid user.

Skill — hands on

On the Mac, print the public key:

cat ~/.ssh/id_ed25519.pub

One line of output ends the step. Go to the paragraph about the server. A message that reads No such file or directory means that this Mac holds no key, and the next paragraph makes one.

CAUTION: Do not run ssh-keygen on a path that already holds a key. The command offers to overwrite the private key, and a typed y destroys that key. Every server that trusts the old key then refuses your login.

Run ssh-keygen with a new path, so that the command cannot touch an existing key. Press Return two times at the passphrase prompt:

ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_vps -C "hermes-vps"
cat ~/.ssh/id_ed25519_vps.pub

The -C option sets the comment at the end of the public key. The comment is a label, and the comment plays no part in the login. A default comment reads user@hostname, which records the hostname of the Mac at the time of the command. A comment such as hermes-vps names the purpose instead.

Use the path of the key that you printed for the rest of this lesson. The next paragraph writes one of these two public keys into the file on the server.

On the server, write that one line into the file that SSH reads:

sudo mkdir -p /home/hermes/.ssh
echo 'PASTE-THE-KEY-LINE-HERE' | sudo tee /home/hermes/.ssh/authorized_keys > /dev/null
sudo chown -R hermes:hermes /home/hermes/.ssh
sudo chmod 700 /home/hermes/.ssh
sudo chmod 600 /home/hermes/.ssh/authorized_keys
sudo ls -ld /home/hermes/.ssh
sudo cat /home/hermes/.ssh/authorized_keys

The command ls -ld shows hermes hermes as the owner, and it shows drwx------ as the mode. The command cat shows one line that ends with your comment. A different owner makes the login fail with no message on the server.

SSH refuses a key file that other users can write. The two chmod commands are a condition of the login, not a precaution.

Knowledge — why tee, and not a redirect

The second command uses tee for one reason. A redirect such as sudo echo 'text' > /home/hermes/.ssh/authorized_keys fails with the message Permission denied.

The shell reads the whole command line first. The shell opens the file for the redirect, and only then starts sudo. So the ubuntu account opens the file, and the ubuntu account cannot write into a directory that root owns.

tee moves the write into the command itself. sudo elevates tee, and tee opens the file as root. The same rule covers every file under /etc and every other root-owned path.

Open a second terminal on the Mac. Keep the first session open. Then test the key:

ssh hermes@SERVER 'whoami'

The command prints hermes and asks for no password. A password prompt means that one of the five commands failed. Correct the error from the first session.

A Mac with several keys needs one more step. A file at ~/.ssh/config can force a different key for a host, so name the key and the server in one block:

Host hermes-vps
  HostName SERVER
  User hermes
  IdentityFile ~/.ssh/id_ed25519_vps
  IdentitiesOnly yes

The command ssh hermes-vps then replaces ssh hermes@SERVER. Task 5 uses the same short name for rsync.

Four profiles become four independent units

Knowledge

get_service_name() at line 1797 builds the unit name from HERMES_HOME. Its own docstring states the rule:

Default ``~/.hermes`` returns ``hermes-gateway`` (backward compatible).
Profile ``~/.hermes/profiles/coder`` returns ``hermes-gateway-coder``.

So this roster becomes four units: hermes-gateway-crazydave, hermes-gateway-peashooter, hermes-gateway-sunflower and hermes-gateway-torchwood.

Four units let Task 5 start the bots one at a time, and stop after the first failure. Four units also let you restart one bot later. The other three bots continue to answer during that restart.

Swap is not a speed setting

Knowledge

Four gateways idle at 181 MB together on the Mac. The measured values are 50.2, 45.1, 43.7 and 42.1 MB. That total is 4.5% of 4 GB, and it looks like sufficient room.

The idle total is not the number that decides the swap size. The gateway runs the agent inside the same process, so the memory grows while a bot answers. A language server adds 200 MB to 500 MB. Four bots that do code work at the same time can reach about 2 GB.

Linux with no swap does not become slow when the memory runs out. Linux stops a process. The kernel selects the largest process, which here is a bot in the middle of an answer.

Skill — hands on 
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
free -h

The Swap: row of free -h reads 2.0Gi in the total column. The new line in /etc/fstab restores the swap file after a reboot.

The chmod 600 is not decoration. swapon refuses a swap file that other users can read.

Measure the route to the two hosts that matter

Skill — hands on 
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://api.telegram.org
curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' https://api.anthropic.com

Each command prints an HTTP code and a time. Both hosts sit outside Indonesia. The quality of the international route is the real product of this purchase.

CAUTION: A time of more than 1 second to either host is a stop condition. Stop before Task 3 and report both times. A slow route gives a slow answer from every bot, every time, and no later step repairs the route.
