Lesson 21 of the Stage 3 build

The first exception that writes

Every exception Crazy Dave has so far only reads and talks. This one runs a command that changes the shared board, and it cannot be taken back. That single difference decides how the clause has to be written.

Why this exception is a different kind

Knowledge

Lesson 20 closed the board questions exception with two limits, and the second one said this: if the message asks you to archive, edit, close, assign, or run anything, the HARD RULE applies. That limit worked exactly as written. You listed the noise tasks, asked Crazy Dave to remove them, and got task t_bc7c0f90 — Remove noise tasks — filed for a specialist to do later.

The limit was drawn in the wrong place. It separated reading from writing, and a coordinator that cannot write to its own board is not a coordinator. Archiving a task is bookkeeping about the board. It produces nothing a specialist would produce, so routing it to a specialist adds a task instead of removing one.

The line that matters is not read against write. It is work for the team against maintenance of the board. Work goes to the board. Maintenance of the board is Crazy Dave's own job, because Crazy Dave owns the board.

Knowledge — what archive really does

Read these four facts before you grant the capability. All four come from hermes_cli/kanban_db.py, in archive_task at line 5542 and promote_task at line 5092.

  1. Archived is terminal. promote accepts only a todo or a blocked task, and it refuses everything else by status. No command returns a task from archived. The row survives, and hermes kanban list --archived still shows it, but the task never runs again.
  2. Archive releases a running task. The update clears claim_lock, claim_expires and worker_pid, then closes the open run with outcome reclaimed and the summary "task archived with run still active". This is why archive is also the cancel command. Note what it does not do: nothing in that function signals the worker process that Hermes already started.
  3. Archiving a parent releases its children. The comment in the source is direct: "archived parents no longer block children, same as done". The function then calls recompute_ready immediately. Archive a parent and its children become ready, so the dispatcher spawns workers for them within the minute. On this board, archive can start work.
  4. --rm is the destructive one. hermes kanban archive --rm <id> calls delete_archived_task, which removes the row and its related rows for good.

Fact 3 is the one that turns a tidy-up request into an incident. "Archive the noise ones" is a safe sentence only while none of those tasks is a parent.

Why the four limits are these four

Each limit answers one fact from the second knowledge box, and no limit asks Crazy Dave to judge how important a request is.

  • Say the ids, then archive, then report. Fact 1: the change is terminal. You cannot review the list afterwards and undo it, so the list has to appear before the command runs.
  • Ask when no task is named. Fact 1 again. "Can you remove it?" after a list of six ids has no safe reading, and a question costs one message.
  • Never --rm. Fact 4. Archive keeps the row and the history. Purging removes both, and no chat message is worth that.
  • Check for children first. Fact 3. This is the limit that stops a tidy-up from starting three workers.

Compare this with the two limits in Lesson 20. Those were drawn from what could go wrong in a conversation. These four are drawn from what one function does to a database. A destructive verb earns the second kind.

The third widening of one file in one day

Count the changes to Crazy Dave's SOUL.md so far: identity questions, triage, dispatched work, small talk, board questions, judgement about the board, and now board maintenance. Seven, and every single one came from a real message rather than from review.

That record is not a failure of review. It is what an enumerated rule costs. A rule that says "use your judgement" needs no revision and gives no guarantee, and Lesson 3 already showed what that wording is worth on a real model. A rule that names moments is testable, so every gap in it appears as one specific message that behaved wrong. The list converges through use, and the price of the guarantee is paid in edits like this one.

Why must Crazy Dave run hermes kanban show before it archives a task?

Right. archive_task calls recompute_ready, and an archived parent no longer blocks a child. A request to remove noise can spawn workers within the minute.

The opposite happens. The update clears the claim and closes the run with outcome reclaimed, which is why archive doubles as cancel.

The update carries AND status != 'archived' and simply changes nothing. Only --rm deletes a row.

What is the boundary this exception actually draws?

Right. Crazy Dave owns the board, so maintaining it is coordinator work. Reading against writing was the wrong line, and it filed a task to delete tasks.

Archive is the least safe command in this lesson, and it is the one Dave now runs. Risk sets the limits, not the owner.

Speed is the reasoning the hard rule bans by name. "Just in case it is faster" is how a coordinator becomes a third specialist.
