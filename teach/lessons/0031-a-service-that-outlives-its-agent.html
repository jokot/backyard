Lesson 31 of the Stage 4 build

A server an agent starts dies at request 978

On 14 September two web servers stopped answering while their ports stayed open. Both had inherited the standard error pipe of the agent that started them. This lesson reproduces the failure on demand, measures the exact request that kills it, and writes the one rule that prevents it into the soul file of Peashooter.

What an agent leaves behind

Knowledge

An agent is a short process by design. It reads a request, runs commands, answers, and exits. A web server is a long process by design. When the agent starts the server as its own child, the two lifetimes disagree, and the child keeps every file descriptor the parent handed it.

Standard output and standard error are the dangerous two. A terminal gives the child a character device. An agent gives the child a pipe, because the agent wants to read the command output and report it back to you.

A pipe is a fixed buffer with a writer at one end and a reader at the other. When the buffer is full, the next write does not fail and does not return. It blocks, and it waits for the reader to take bytes out.

The agent exits. The reader is gone. The buffer never drains again.

Why the port stays open

Knowledge

python3 -m http.server writes one log line to standard error for every request it serves. That log line is the trap.

The server accepts a connection, writes the log line, and then writes the response. When the pipe is full, the server stops inside the log write and never reaches the response. It holds the connection open and answers nothing.

The socket stays in LISTEN, because the kernel owns the socket, not the process. The kernel keeps accepting connections into a queue that nobody reads. Every diagnostic that asks the kernel reports a healthy service.

This is why the failure of 14 September looked impossible. lsof showed a listener. The port answered a connection. ngrok reported HTTP 503. Only a real request exposed the truth.

An open port is not a working service

LISTEN says the kernel holds the socket. It says nothing about the process behind it. Test a service with a request, never with lsof:

curl -sS -o /dev/null -w '%{http_code}\n' --max-time 5 http://127.0.0.1:8000/

A blocked server returns curl: (52) Empty reply from server or a timeout. A working server returns 200.

Do this now — reproduce the failure

Skill — hands on

Read the number off your own machine. Do not trust the number in this lesson.

Step 1. Measure the pipe buffer. Write into a pipe that has no reader until the write refuses:

python3 - <<'PY'
import os, fcntl, errno
r, w = os.pipe()
fcntl.fcntl(w, fcntl.F_SETFL, os.O_NONBLOCK)
total = 0
try:
    while True:
        total += os.write(w, b"x" * 1024)
except OSError as e:
    if e.errno not in (errno.EAGAIN, errno.EWOULDBLOCK): raise
print(f"pipe blocks after {total} bytes")
PY

This machine reported 65536.

Step 2. Measure one log line. Start a server, send one request, and count the bytes:

python3 -m http.server 8901 --directory /tmp 2>/tmp/hs.err &
curl -s -o /dev/null http://127.0.0.1:8901/
awk '{print length($0)+1, "bytes"}' /tmp/hs.err

This machine reported 67 bytes, from the line ::ffff:127.0.0.1 - - [16/Sep/2026 18:57:03] "GET / HTTP/1.1" 200 -.

Step 3. Predict the request that kills the server. Divide the buffer by the line:

65536 / 67 = 978

Step 4. Run the prediction against a real server. Save this file as repro.py and run it:

import subprocess, os, sys, time, urllib.request

p = subprocess.Popen(
    [sys.executable, "-m", "http.server", "8902", "--directory", os.getcwd()],
    stdin=subprocess.DEVNULL, stdout=subprocess.PIPE, stderr=subprocess.PIPE,
)
for _ in range(200):
    try:
        urllib.request.urlopen("http://127.0.0.1:8902/", timeout=0.5).read(); break
    except Exception: time.sleep(0.05)

n = 0
try:
    while n < 5000:
        n += 1
        urllib.request.urlopen("http://127.0.0.1:8902/", timeout=2).read()
except Exception as e:
    print(f"server stopped answering at request {n}")
subprocess.run(["lsof", "-a", "-p", str(p.pid), "-d", "0,1,2"])
p.kill()

The stderr=subprocess.PIPE line is the whole defect. It is what an agent does every time it starts a server and wants to read the output.

The measured result

Two runs on 16 September 2026 gave the same answer:

server stopped answering at request 978
pipe bytes written before block: about 65526

Python 31456 jokot 1 PIPE 0x193f...  16384 ->0x2630...
Python 31456 jokot 2 PIPE 0x8dad...  65536 ->0x2712...

978 requests times 67 bytes is 65,526 bytes, against a buffer of 65,536. The prediction and the measurement agree to within one log line.

Read the two pipe sizes in that output. Descriptor 1 stayed at 16,384 because nothing wrote to it. Descriptor 2 grew to 65,536 because the log filled it. macOS gives a pipe 16,384 bytes and grows it on demand.

That growth makes the SIZE/OFF column a trap. A third server, planted on port 8904, reported both descriptors at 16384 while it was still healthy. The arithmetic on that reading predicts request 244. The server answered 978 requests and then stopped, because the buffer grew under the load that was filling it.

Take 978 as the number for this machine, from three runs. Take the reading from lsof as a snapshot of the buffer now, never as its limit.

The fix, and the proof

Skill — hands on

Send the output to a device that never fills, and detach the process from the agent:

nohup python3 -m http.server 8000 --directory <dir> >/dev/null 2>&1 &

Keep the log when you want it. A file has no buffer limit and no reader requirement:

nohup python3 -m http.server 8000 --directory <dir> >>/tmp/http8000.log 2>&1 &

Run the same load against the repaired server. Change the two subprocess.PIPE values to subprocess.DEVNULL and raise the limit to 2000 requests. The result on 16 September 2026:

still answering after 2000 requests, which is 134000 bytes of log

Python 31516 jokot 0u CHR 3,2 /dev/null
Python 31516 jokot 1u CHR 3,2 /dev/null
Python 31516 jokot 2u CHR 3,2 /dev/null

134,000 bytes is more than twice the buffer that killed the first server. All three descriptors name a character device.

Diagnose a silent process by its descriptors

Knowledge

The logs are exactly what the process cannot write, so the logs cannot report this failure. Two commands give the answer instead.

The first command names the parent:

ps -o pid,ppid,etime,command -p <pid>

A parent process id of 1 means the agent that started this process has exited. The process is an orphan, and launchd adopted it.

The second command names the cause:

lsof -a -p <pid> -d 0,1,2

Read the TYPE column. CHR pointing at /dev/null is safe. REG pointing at a log file is safe. PIPE on an orphan is the defect, and the SIZE/OFF column states how many bytes the process may still write before it stops.

The server from record 0038, two days later

The repair of 14 September still holds. The same process id answered on 16 September 2026:

A parent process id of 1 with three character devices is the shape you want. The process is an orphan on purpose, and it writes nowhere.

Do this now — write the rule where it fires

Skill — hands on

Record 0038 stated this rule on 14 September and changed no file. Its own status line says so: "Fixed for this server. The pattern remains in the prompts."

Record 0042 gives the test that this fails. After you state a rule, ask what would change on the machine if the rule were false. Nothing changed. The rule was a note.

Peashooter is the profile that builds and runs software, so the rule belongs in the soul file of Peashooter. Add this block:

Starting a long-lived service — HARD RULE: you are a short process and a
server is a long one. Never start a server in the foreground, and never
let it inherit your standard output or standard error. Both are pipes
that nobody drains after you exit, and a full pipe stops the server
inside a log write while its port stays open. Always redirect and
detach:

  nohup <command> >/dev/null 2>&1 &

Use a log file instead of /dev/null when you need the output:

  nohup <command> >>/tmp/<name>.log 2>&1 &

Verify before you report the service running. Run both commands and
paste both results:

  lsof -a -p <pid> -d 0,1,2
  curl -sS -o /dev/null -w '%{http_code}\n' --max-time 5 http://127.0.0.1:<port>/

Descriptors 1 and 2 must not say PIPE. The curl must print a status
code. An open port is not a working service.

Write the same block into the soul file of any later profile that runs software. The rule belongs to the job, not to the plant.

The command that fails when the rule is broken

Knowledge

Record 0042 asks every rule for a command that fails when the rule is broken. This rule has one. Run it against every listener you own:

for pid in $(lsof -nP -iTCP -sTCP:LISTEN -t 2>/dev/null | sort -u); do
  [ "$(ps -o ppid= -p "$pid" 2>/dev/null | tr -d ' ')" = "1" ] || continue
  lsof -a -p "$pid" -d 1,2 2>/dev/null | grep -q PIPE \
    && echo "AT RISK  $pid  $(ps -o comm= -p "$pid" | sed 's#.*/##')"
done
echo "audit complete"

The test for the parent process id is not optional, and the first version of this audit omitted it. Without that test the audit reported six processes on this machine, and all six were healthy. Five belonged to Cursor and one to Stremio, and every one had a living parent that drains its pipe.

A pipe is a defect only when nobody reads it. A parent process id of 1 is the cheap test for that, because it means the process that held the other end has exited.

The audit was checked against all three cases. It named the planted failure on port 8904. It stayed silent about the six processes with a living parent. It stayed silent about process 32523, which has a parent process id of 1 and writes to /dev/null.

One limit stays open. A parent that is still alive and never reads its pipe produces the same failure, and this audit does not see it. Redirection at start is the rule. The audit is the net under it.

A server answers for hours, then stops while its port stays in LISTEN. What does this most likely mean?

Right. The kernel holds the socket, so LISTEN survives a process that cannot speak. The delay is the buffer filling one log line at a time.

A memory failure ends the process, and the port closes with it. This port stayed open, so the process is alive and stopped.

The local port failed the same test as the tunnel. A request to 127.0.0.1 returned an empty reply, which puts the fault behind the socket.

Why can the logs of a blocked server never report this failure?

Right. The process stopped inside the log write, so the message describing the fault is the message that cannot leave. Read the descriptors instead.

No file exists to delete. The output went to a pipe in memory, which is why no file appears anywhere on disk.

A pipe drops nothing and overwrites nothing. It stops the writer instead, which is the whole mechanism of this failure.
