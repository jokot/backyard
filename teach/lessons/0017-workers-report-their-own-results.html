Lesson 17 of the Stage 2 build

Let the worker speak

Stage 2 finished its first unattended run and then sent the same completion messages every two minutes for six hours, from three different bots. The work was correct. The reporting layer was not. This lesson removes that layer.

What the notifier actually is

Knowledge

Hermes reports finished kanban work through a subscription table called kanban_notify_subs. Every gateway polls it every five seconds, claims unseen events, and sends them out its own bot. The design assumes one gateway. Stage 2 runs three.

Three properties of that table combined into one failure. Its cursor column is declared last_event_id INTEGER NOT NULL DEFAULT 0, so a new row replays every past event on its task. Its delivery path deletes a row after repeated send failures (gateway/kanban_watchers.py:461). And every gateway sees every row, because they all read one ~/.hermes/kanban.db.

Lesson 16 met the first symptom: a blocked child reported to nobody, recorded in learning record 0008. The repair was a cron job that re-subscribed every task each minute. That repair closed a loop — the gateway deleted the row, the cron job replaced it at cursor zero, and the replay started again. Full detail in learning record 0010.

Read the format before calling it broken

The delivered line looked wrong in three ways at once:

✔ [default] @peashooter Kanban t_64e9b555 done — Serve Flappy Bird

The source at gateway/kanban_watchers.py:336 explains every part of it:

board_tag = f"[{board_slug}] "
who = (task.assignee if task and task.assignee else None)
tag = f"@{who} " if who else ""
title = (task.title if task else sub["task_id"])[:120]

[default] is the board name, not a profile. @peashooter is the task assignee, not the sending bot. The cut-off text is a 120 character limit on the title. None of that is a defect. It reads as nonsense only because the wrong bot delivers it, so an @peashooter line arrives inside Crazy Dave's chat and looks like one bot tagging another.

The lesson generalizes past this file. Before you call output broken, find the line that produced it. Half of what looked like three bugs here was one bug plus a naming choice.

The reference architecture solves it by deleting it

Knowledge

Zain Fathoni's write-up of the same idea — named back in Lesson 1 — records this exact lesson from the other side. He built an in-house task abstraction called "beads", found it unreliable, and abandoned it. His stated rule is to use a real task management system rather than a homebrew abstraction.

His specialists report their own results. There is no subscription table, so no cursor can reset and no second process can claim a row. The agent that did the work speaks, through its own bot, in its own words. That single change removes the wrong-bot problem, the template format, and the replay together, because all three live in the layer being deleted.

Do this now

Skill — hands on

1. Stop the loop — remove the cron job, then empty the subscription table:

hermes cron list
hermes cron remove <job_id>
sqlite3 ~/.hermes/kanban.db "DELETE FROM kanban_notify_subs;"
rm -f ~/.hermes/profiles/crazydave/scripts/kanban-autosubscribe.sh

2. Confirm each profile owns a separate bot token. This is what makes a worker able to speak as itself:

for p in crazydave peashooter sunflower; do
  printf "%-12s " "$p"
  grep -h TELEGRAM_BOT_TOKEN ~/.hermes/profiles/$p/.env | cut -c1-32
done

Three different token prefixes means three different bots.

3. Add the reporting rule to each SOUL.md. For Peashooter and Sunflower:

Reporting finished kanban work — HARD RULE: when the dispatcher gives
you a kanban task and you finish it, tell Jokot yourself before you complete
the task. Run this in the terminal:

  hermes send --to telegram:<your_chat_id> "your message here"

Write two or three sentences in your own voice. Say what you did, give the
full path of every file you changed, and state what you verified. Do not
repeat the task id or the task title back — Jokot already knows what he
asked for. Send exactly one message for each task. If you blocked instead of
finishing, use the same one message to say what you need.

Crazy Dave closes root tasks rather than doing specialist work, so its wording differs:

Reporting a finished root task — HARD RULE: when you complete a root
task whose children are done, tell Jokot yourself before you complete it. Run
this in the terminal:

  hermes send --to telegram:<your_chat_id> "your message here"

Write a short summary of the whole job in your own voice. Say what exists
now, where it lives, and anything Jokot must do himself. Do not list the
child task ids. Send exactly one message for each root task.

4. Test the path by hand before trusting an agent to it:

hermes send --to telegram:<your_chat_id> "reporting path works"
Why hermes send and not a tool call

Hermes ships a send_message tool, and agents cannot call it. It appears in no toolset list. The comment at toolsets.py:374 states the rule and names the supported entry point:

agents do NOT get an agent-callable send_message tool — outbound platform
messaging is handled outside the agent loop (cron delivery, the gateway
kanban notifier, and the `hermes send` CLI)

Agents do hold the terminal tool, so hermes send is reachable. It reuses the same platform credentials the gateway uses, which is why a Peashooter worker running it speaks through Peashooter's bot rather than a shared one.

The cron job re-subscribed every task once a minute. Why did that turn a silent failure into a repeating one?

Right — last_event_id INTEGER NOT NULL DEFAULT 0. The gateway deleted the row after send failures, the cron job replaced it at zero, and the completed event was delivered again. The loop had no exit.

Frequency was not the fault. A script that re-created rows once an hour would have replayed the same events, just more slowly.

They share one ~/.hermes/kanban.db. Sharing it is what let every gateway see every row, but the replay came from the cursor default.
