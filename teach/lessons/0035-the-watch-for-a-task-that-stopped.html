Lesson 35 of the Stage 5 build

A second scheduled script reads the kanban board directly, because a worker that stops sends no report

Record 0043 found the gap this lesson closes: a worker that stops before it reports leaves its task blocked in silence, with no reader to see it. This lesson adds a second cron job, blocked-watch, that reads the kanban board directly instead of a worker's report. The lesson also examines kanban-autosubscribe.sh, and it explains why Stage 5 does not schedule that script. Together with roster-audit from Lesson 34, two cron jobs then run on the machine.

The report script cannot see a worker that never speaks

Knowledge

hermes-report.sh, from Lesson 32, runs only when a worker calls it. A worker that stops before it reports sends no message at all, and the task stays blocked in silence.

Record 0043 named two tasks that blocked on 14 September 2026, t_8e9c7cfb and t_34115dfd. The kanban board held both blocked states correctly the whole time. Only a reader was missing.

The SQLite precedence trap

Knowledge

The wrong expression divides a string by a string:

SELECT 'blocked ' || (1000 - 400)/60 || 'm';
-- returns 0

In SQLite, the || operator binds tighter than - and /, so both concatenations run before the division. The expression groups as ('blocked ' || (1000 - 400)) / (60 || 'm'), which reduces to 'blocked 600' / '60m', a string divided by a string. SQLite casts each string operand to a number before it divides them. 'blocked 600' casts to 0, so the whole expression returns the integer 0. Parentheses around the arithmetic fix the order:

SELECT 'blocked ' || ((1000 - 400)/60) || 'm';
-- returns blocked 10m

The script in full

Skill — hands on

Write this file at ~/.hermes/profiles/crazydave/scripts/blocked-watch.sh. Copy every line, including every comment:

#!/usr/bin/env bash
# Print one line for each kanban task that stayed blocked for more than 60
# minutes. Print nothing otherwise, so a healthy run delivers no message.
#
# The script opens kanban.db without `-readonly`. A read-only connection to
# a WAL database fails when the -shm and -wal sidecar files are absent, and
# those files exist only while a writer holds the database open. This query
# is a SELECT and changes nothing.
set -uo pipefail
DB="${HERMES_KANBAN_DB:-$HOME/.hermes/kanban.db}"
[ -f "$DB" ] || exit 0
sqlite3 "$DB" <<'SQL' 2>/dev/null
SELECT 'blocked ' || ((strftime('%s','now') - e.created_at)/60) || 'm: '
       || t.id || ' (' || COALESCE(t.assignee,'unassigned') || ') '
       || substr(COALESCE(json_extract(e.payload,'$.reason'),''),1,120)
FROM tasks t
JOIN task_events e ON e.task_id = t.id AND e.kind = 'blocked'
WHERE t.status = 'blocked'
  AND e.created_at = (SELECT MAX(created_at) FROM task_events
                      WHERE task_id = t.id AND kind = 'blocked')
  AND e.created_at < strftime('%s','now') - 3600;
SQL
exit 0

Create the folder if it does not exist yet, then make the file executable:

mkdir -p ~/.hermes/profiles/crazydave/scripts
chmod +x ~/.hermes/profiles/crazydave/scripts/blocked-watch.sh

Prove the formatting

Skill — hands on

sed -e "s/t.status = 'blocked'/1=1/" \
    -e "s/e.created_at < strftime('%s','now') - 3600/1=1/" \

The repair this stage does not schedule

Knowledge

kanban-autosubscribe.sh still sits in ~/.hermes/scripts/. An earlier draft of this lesson repaired line 14, moved the file into the profile scripts folder, and created a cron job named kanban-autosubscribe on a 15-minute schedule. That plan was wrong, and record 0010 already said so.

Record 0010 measured the cost. The same script, on a one-minute schedule, delivered one message every two minutes for six hours. The record states the fix in one line: delete the notifier path rather than repair it. Lesson 17 carried out that deletion, and it removed the profile copy of this file.

The loop needs four steps, and all four still work today:

  1. The cron job subscribes a task at cursor zero.
  2. The gateway replays every past event and delivers it.
  3. One failed send drops the subscription row.
  4. The next cron tick subscribes the same task again.
Both conditions are still in the source

Read the installed source before you trust any claim about a loop that closed years ago. Two greps settle it.

grep -n 'last_event_id INTEGER NOT NULL DEFAULT 0' \
  ~/.hermes/hermes-agent/hermes_cli/kanban_db.py
grep -n 'MAX_SEND_FAILURES' \
  ~/.hermes/hermes-agent/gateway/kanban_watchers.py

The first grep prints lines 1263 and 2154. A new subscription row starts at cursor zero, so it replays history. The second grep prints line 457, where three consecutive send failures call _kanban_unsub and drop the row. Step 1 and step 3 of the list above are therefore both live.

Leave the file where it is. Do not repair line 14, and do not create the job. A repair that runs on a schedule turns a failure that happens once into a failure that happens forever.

Why blocked-watch is different

blocked-watch.sh writes nothing. It runs one SELECT against kanban.db and prints the result. It creates no subscription row, so no cursor can reset and no second process can claim the row. The script reads state, and the autosubscribe script created state. That difference is the whole reason one job is safe and the other is not.

Create the second cron job

Skill — hands on 
hermes -p crazydave cron create 'every 1h' \
  --name blocked-watch --script blocked-watch.sh --no-agent --deliver telegram

The command passes a bare filename, per the rule Lesson 34 already taught. The filename resolves under $HERMES_HOME/scripts, which hermes -p crazydave sets to ~/.hermes/profiles/crazydave/scripts.

The command prints the 12-character job id. This run printed f9b05a451c28, and every 1h stored as every 60m.
