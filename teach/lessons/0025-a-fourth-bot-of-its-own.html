Lesson 25 of the Stage 4 build

The clone brings its own identity

Stage 4 adds Torchwood, the agent that writes your prompts. Creating it takes one command. That command also copies a live secret from Peashooter, and a reader who does not know this ends up with two profiles wearing the same face.

Why a prompt agent, and why first

Knowledge

Two defects in this project were prompt defects, not code defects. Learning record 0016 describes a specification that passed review with tests_run: 0 and stated a formula that could not work. Record 0018 describes a task that named no durable destination, so the finished artifact disappeared with the scratch workspace that held it.

Neither agent was wrong about code. Both were asked a question that did not say where the answer had to land, or how anyone would know it worked. Torchwood exists to make those two things mandatory before the work starts.

It goes first because it multiplies the other three agents on your list. A better brief improves whatever receives it. It is also the cheapest to get wrong: Torchwood produces text and writes no file, so a bad output costs you one reread.

The trap inside one flag

Knowledge

Run hermes profile create --help and read the description of --clone:

Copy config.yaml, .env, SOUL.md, and skills from active profile

Four things, and the second one matters. A .env file holds live secrets. Peashooter's holds TELEGRAM_BOT_TOKEN, which is the identity of the Peashooter bot. A token is not a setting that points at a bot. A token is the bot.

So a clone that keeps that value produces two gateway processes polling Telegram for the same bot. Telegram hands each update to whichever asked most recently, so replies arrive from the wrong agent at random, and nothing reports an error. This is the failure shape Stage 1 already met in record 0006: a Telegram step that reports no error and leaves the wrong state behind.

The lesson therefore replaces the token as its own step, with its own check. A step that hides inside another step is a step that does not happen, which is what record 0019 cost this project at the end of Stage 3.

Do this now

Skill — hands on

1. Create the bot. Open a chat with @BotFather and send /newbot. Give it a display name and a username ending in bot. Copy the token it returns. It looks like 1234567890:AA....

Then send /mybots, choose the new bot, choose Bot Settings, choose Group Privacy, choose Turn off. A bot with group privacy enabled receives only messages that name it, so it can never act as a default listener. Lesson 18 records the same rule.

2. Create the profile.

hermes profile create torchwood --clone-from peashooter

Expected: a new profile and a new wrapper script at ~/.local/bin/torchwood. That wrapper runs hermes -p torchwood "$@", which is how every later command in Stage 4 selects this profile.

3. Replace the token. This is the step from the section above. Print the path first:

hermes config env-path -p torchwood

Open that file. Replace the value of TELEGRAM_BOT_TOKEN with the token from step 1. Then check the file without printing any secret:

grep -c '^TELEGRAM_BOT_TOKEN=' "$(hermes config env-path -p torchwood)"

Expected: 1. A count of 2 means the file holds two lines for the same key. The last line wins, so delete the older one.

4. Reset the inherited memory. The help text lists four things the clone copies. It copies a fifth. Record 0005 found Peashooter carrying notes about an unrelated Go project after a clone, because --clone-from also copies memories/MEMORY.md and memories/USER.md.

hermes -p torchwood memory reset --yes --target memory

Use --target memory and not --target all. MEMORY.md holds the working notes Peashooter wrote about its own tasks, and Torchwood should not start life believing it did that work. USER.md holds facts about you, which stay true whichever agent reads them, and a prompt writer that already knows your stack asks fewer questions.

Check what survived:

ls -l ~/.hermes/profiles/torchwood/memories/

Expected: USER.md and no MEMORY.md. The reset deletes the file rather than emptying it, so a missing MEMORY.md is the pass. Do not check this with wc -c, which reports an error for a missing file and reads like a failure.

5. Choose the model.

hermes -p torchwood config set model.default openai/gpt-5.6-luna
hermes -p torchwood config get model.default

Expected: the second command prints openai/gpt-5.6-luna. Peashooter runs deepseek/deepseek-v4-flash-0731 and Sunflower runs z-ai/glm-5.3-flash, so this is a deliberate step up. Every failure Torchwood can have is a failure to follow an instruction, such as naming a path no command confirmed. At roughly five interviews a day, the stronger model costs little.

6. Mirror the configuration into the repository. Copy in the same session that made the change:

mkdir -p hermes-config/torchwood
cp ~/.hermes/profiles/torchwood/config.yaml hermes-config/torchwood/config.yaml
grep -c 'gpt-5.6-luna' hermes-config/torchwood/config.yaml

Expected: 1. A count of 0 means the copy never ran. Never copy .env or auth.json into the repository. Those files hold live secrets.

You skip the token step and start both gateways. You send ten messages to the bot. About half receive no reply at all, and the replies that do arrive do not share one voice. What is the cause?

Right. The --clone-from flag copies .env, and the token in that file is the bot. Telegram hands each update to one poller only, chosen by timing. Note the symptom: there is one bot account, so no reply carries a different sender. The loss and the changing voice are the evidence.

True, and it is not this symptom. A copied SOUL.md changes what every reply says, and it loses no message. Half the messages vanished here, which only a second poller explains.

Hermes keeps no pool of bots. Every bot comes from @BotFather, and a profile reaches exactly the one bot whose token sits in its own .env file.

The token is replaced, the check prints one, and the gateway runs. You ask the new bot who it is. It answers that it is Peashooter. What is the cause?

Right, and the help text says so. Line 1 of that file names Peashooter. Lesson 28 replaces the file. Until then the answer proves the clone worked, and it reports no fault.

The check in step 3 prints one token line, and step 2 gave that token a separate bot. A wrong token loses messages. It does not rename a bot that answers.

A model is a supplier of text, and it carries no name of its own. Torchwood runs openai/gpt-5.6-luna and Peashooter runs a DeepSeek model, and both answer to whatever SOUL.md says.

Checkpoint

Two things the clone also carried, and neither is a defect.

The first is SOUL.md. Send the new bot a private message asking who it is, and it answers Peashooter, because the file that tells it who it is arrived byte for byte from Peashooter. The help text says so. A profile at the end of Lesson 25 owns a bot, a model, and a clean memory, and it owns no identity yet. Lesson 28 replaces SOUL.md in full. Until then, read the answer as proof that the clone worked, not as a fault.

The second is free_response_topics, which still names thread 2. Torchwood would answer every unnamed message in #Coding today, beside Peashooter. Do not start the gateway as a service until Lesson 26 gives Torchwood a topic of its own.
