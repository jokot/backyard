Lesson 22 of the Stage 3 build

Five claims, five checks

Everything is built. One request now has to travel from a topic in the group, through the coordinator, into a Fizzy card, out to two specialists, back as two Telegram reports, and end with a closed card. This lesson runs that request and refuses to take anyone's word for any part of it.

Why a passing check is not a passing claim

Knowledge

Stage 2 ended with a bot reporting a live game server. The report was true. Fifteen minutes later the server returned nothing at all. The cause is in learning record 0011: the process had no file descriptor 1 and no descriptor 2, because they closed when the agent session that started it ended, and Python's http.server writes a log line before it writes a single response byte.

The generalization is the rule for this whole lesson. A worker cannot test its own afterlife. Some claims are not about an instant. "The server is running" is a claim about every moment after the check, including moments the worker cannot observe. So verify the structure that keeps a claim true, not the claim. An open file descriptor is checkable now and predicts later. An HTTP 200 is checkable now and predicts nothing.

Applied here: do not accept "the card is closed" or "both bots reported". Read the board, read Fizzy, read the messages.

Do this now

Skill — hands on

1. Send one cross-domain request in #General. It must genuinely need both specialists, so that decompose produces children with different assignees. The Stage 2 shape that worked: ask for a small browser game, specified first and then implemented, with a test run at the end. Write down the exact text you send.

2. Check the card appeared.

fizzy card list --profile crazydave --board <BOARD_ID>

Expected: one new card whose title matches your request.

3. Check the decomposition.

hermes kanban list

Expected: one root task assigned to crazydave, and two or more children assigned to peashooter or sunflower. If children exist but sit in triage forever, re-read the second correction in Lesson 12.

4. Collect the reports verbatim. When the run finishes, write down every Telegram message the bots sent, which bot sent it, and which topic or chat it arrived in. Do not summarize. The check is that each message came from the bot that did the work and that none of them repeat — Lesson 17 removed the layer that used to get both of those wrong.

5. Check the closing half of the mirror.

hermes kanban list
fizzy card list --profile crazydave --board <BOARD_ID>

Expected: the root task reads done, and the Fizzy card is closed and carries a summary comment.

6. Check any claim about something still running. If a report says a server or a URL is live, check the structure, not the claim:

lsof -p <pid>

Descriptors 1 and 2 must both be open, to a real file. If they are missing, the service will fail the moment it tries to write a log line, whatever a browser shows you right now.

Score the five criteria

Skill — record the result

Write down a verdict for each, with the output that supports it. A criterion met by a different mechanism than the spec named is recorded as exactly that, not as a plain pass — Stage 2's spec says so about its own criterion 4, and that honesty is what made the Stage 3 design possible.

  1. An unnamed message in #Coding is answered by Peashooter and by no other bot.
  2. A message naming Sunflower in #Coding is answered by Sunflower and by no other bot.
  3. Each of the three bots answers a private message exactly as it did before Stage 3.
  4. No bot answers an unnamed message in a topic another profile owns.
  5. A cross-domain request in #General produces one Fizzy card, two or more children, one Telegram report per child, and one closed card carrying the summary.

Every real defect gets a learning record — root cause, fix, generalization — never a workaround. That practice is what produced records 0008 through 0012 during Stage 2, and two of those five describe mistakes in the teaching, not in Hermes.

A bot reports that the deployed page is live, and you open the URL and see it. What have you verified?

Right — record 0011 exactly. The Stage 2 server passed this check and then died, because the descriptors it needed to log a request had closed with the session that started it.

A response proves the socket was open at that instant. Durability lives in how the process was started — detached, with stdout and stderr redirected to a real file.

Two different layers. Record 0010 fixed how a message travels. Record 0011 is about content — fixing delivery does not make the message true.
