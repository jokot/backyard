Lesson 27 of the Stage 4 build

The sentence the router reads

Torchwood now owns a room, and the board can already send it work. One command puts a sentence in front of the decomposer that turns it away. This lesson writes that sentence, and then tests it instead of believing it.

Torchwood is already a valid destination

Knowledge

Run hermes kanban assignees today and the new profile is on the list:

NAME                  ON DISK   COUNTS
crazydave             yes       done=8
default               yes       (idle)
peashooter            yes       done=20
sunflower             yes       done=12
torchwood             yes       (idle)

Creating a profile makes it assignable. Nothing else is required. Three profiles run auto_decompose: true with auto_decompose_per_tick: 3 and dispatch_interval_seconds: 60, so a parent task breaks into children without anyone asking, once a minute.

The decomposer chooses an assignee by reading the description field in each profile. An empty description is not a refusal. It is an absence of evidence, and a model that must choose will choose on whatever else it has, which is the profile name.

The precedent you already own

Knowledge

Crazy Dave carries this, in ~/.hermes/profiles/crazydave/profile.yaml:

description: "Template only — never a work destination. Do not assign kanban
  tasks here."
description_auto: false

That line is the Stage 2 fix that stopped work from reaching the coordinator. It has two halves, and both do a job. The first half says what the profile is. The second half says what to do about it, in the words the decomposer uses for its own task, which is assignment.

Torchwood needs the same shape, because it has the same problem. It is a plausible destination for any task with the word prompt in it.

Do this now

Skill — hands on

1. Write the description. One command does the whole job:

hermes profile describe torchwood --text "Interactive prompt writing in the Prompts topic. Never a work destination. Do not assign kanban tasks here."

Expected: Description updated for 'torchwood'.

2. Check both fields.

cat ~/.hermes/profiles/torchwood/profile.yaml

Expected: the description you wrote, and description_auto: false under it. You did not set the second field. The --text path writes it for you, and the next section explains why that matters.

3. Read the next box before you create anything. This test puts a real task on a real board, and three gateways are watching it. Know how you will stop the work before you start it.

4. Create the task, then watch the clock. The word prompt appears twice, and the task is genuinely engineering work:

hermes kanban create --triage "write a prompt for the flappy refactor, then apply the prompt"
hermes kanban list

Read the task id, and check that the status reads triage. You have about 60 seconds.

5. Read the result. Within one tick the board decomposes the task without you:

hermes kanban show <task_id>
hermes kanban list

Expected in show: two events, the second reading decomposed, and a comment signed auto-decomposer. Expected in list: child tasks that name peashooter or sunflower. A child that names torchwood fails this test.

If a full minute passes with one event and no children, run the decomposer yourself:

hermes kanban decompose <task_id>

6. Stop the work, in this order. A child is probably running already. Block the children that have not started, release the one that has, then archive all three:

hermes kanban block <child_id> "Lesson 27 routing test, not real work"
hermes kanban reclaim <running_child_id>
hermes kanban archive <root_id> <child_id> <child_id>
hermes kanban list

Block first and archive second. Archiving a task that a worker holds leaves the worker running against a task that no longer exists on the board.

Why one command is the whole job

Knowledge — read from the source

Two files hold profile settings, and they are not interchangeable.

  • config.yaml holds the runtime configuration, and hermes config set writes it.
  • profile.yaml holds the two routing fields, description and description_auto, and hermes profile describe writes it.

So hermes config set description_auto false writes a key into the wrong file. The command reports success, because config set accepts any key. Nothing then reads that key. The lesson draft for this page carried that exact command until a read of hermes_cli/main.py line 11751 showed the --text path already writing the field:

_profiles_mod.write_profile_meta(
    profile_dir,
    description=text_value,
    description_auto=False,
)

The field is worth understanding rather than copying. description_auto records who wrote the sentence. A machine-written description carries true, and a human-written one carries false. hermes_cli/profile_describer.py line 191 then reads it:

if existing.get("description") and not existing.get("description_auto") and not overwrite:
    return DescribeOutcome(canon, False, "profile already has a user-authored description")

So a later sweep with hermes profile describe --auto --all skips your sentence and cannot replace it. Only an explicit --auto --overwrite on this profile replaces it. Your wording is safe by default, and it is not safe from a deliberate command.

This test dispatches real agents

The board in this course is the board your three agents work from. Every profile runs auto_decompose: true with auto_decompose_per_tick: 3 and dispatch_interval_seconds: 60. A task parked in triage is therefore decomposed inside one minute by the tick, and a child is claimed and started shortly after.

That happened on the first run of this lesson. The reader never typed decompose. Sixty seconds after the create command, the board held this:

t_2c9f7149  todo      crazydave    write a prompt for the flappy refactor, then appy the prompt
t_db020b96  running   sunflower    Write the refactor prompt for the flappy codebase
t_7ae96c4d  todo      peashooter   Apply the flappy refactor prompt to the codebase

The routing was correct, and the second child was a live instruction to change the code in projects/flappy. Read the titles of the children as soon as they appear. A child that only writes text is safe to finish. A child that changes files is not, and step 6 stops it.

Why the task must start in triage

Knowledge — read from the source

A task created without --triage lands in ready, and decompose refuses it. hermes_cli/kanban_decompose.py line 288:

if task.status != "triage":
    return DecomposeOutcome(
        task_id, False, f"task is not in triage (status={task.status!r})"
    )

The command then prints one line to standard error and exits:

kanban: decompose t_b98be7e9: task is not in triage (status='ready')

Read that message carefully, because the board that follows looks almost right. The task exists, it holds the title you wrote, and it has no assignee. Nothing announces that the test never ran. The evidence is the event list. A task that was decomposed carries more than one event.

Triage is where work from Telegram arrives, which is why Stage 3 never needed this flag. Crazy Dave parks a request in triage, and the decomposer takes it from there. A task typed at the terminal skips that step unless you ask for it.

What the decomposer actually reads

Knowledge — read from the source

The decomposer builds a roster from every profile and puts it in the prompt. kanban_decompose.py line 231 builds each entry, and line 247 formats it:

"description": desc or f"(no description; profile named {p.name!r})"
...
tag = "" if entry["has_description"] else " ⚠ undescribed"
lines.append(f"  - {entry['name']}{tag}: {entry['description']}")

So an undescribed Torchwood reaches the model as this line:

  - torchwood ⚠ undescribed: (no description; profile named 'torchwood')

That is the claim from the first section, shown rather than asserted. An empty description does not remove a profile from the roster. It puts the profile name in the description slot, and the name of this one is a word that appears in prompt-shaped tasks.

When a child reaches Torchwood

Do not weaken the test. The test task is deliberately worded to invite the mistake, and making it easier proves nothing.

  1. Record the description the decomposer read and the child it produced. Both go in a learning record, because the next three specialists face the same problem.
  2. Change the description so that it names no work verb. Compare "interactive prompt writing" against "writes prompts". The second reads as a service the board can request.
  3. Run step 3 and step 4 again, unchanged.

Record the wording that failed beside the wording that passed. The difference between those two sentences is the reusable part of this lesson.

You set the description, and a week later somebody runs hermes profile describe --auto --all to fill in the profiles that have none. What happens to your sentence?

Right. The --text path recorded description_auto: false, and the describer skips a profile that carries a description a human wrote. Only --auto --overwrite replaces it.

That command writes a key into config.yaml, and the router reads profile.yaml. It reports success and changes nothing. One command already did the whole job.

The flag --all means every profile that is missing a description. The function that builds the list drops any profile that already holds a description a human wrote.

A decompose run sends one child to Torchwood. Which response keeps the evidence that the next three specialists need?

Right. The pair of sentences is the finding. A rule that says which words attract work is reusable, and a description that happens to work today is not.

That moves the test until it passes. The task is worded to invite the mistake on purpose, because a real request one day carries the same words and nobody rewords that one.

A repair by hand fixes one task and leaves the cause. The board dispatches once every 60 seconds, and nobody watches every tick.

Checkpoint

Torchwood now refuses work in the one place a router looks. It still answers in the voice of Peashooter, because SOUL.md arrived with the clone. Lesson 28 replaces that file, and it states the same limit a second time. Two statements of one limit is not duplication here. The description guards the board, and the soul guards the conversation.
