Lesson 8 of the Stage 2 build

A hard rule from the first draft

Peashooter's scope boundary started soft and had to be hardened after a real failure (Lesson 3). Sunflower gets the hardened wording from the start — the lesson learned, applied a second time, before it is needed instead of after.

Why "hard rule" wording matters

Knowledge A SOUL.md that politely says a topic is "outside scope" competes with the rest of the system prompt for the model's attention — with a cheap model, the polite version often loses. Peashooter's Lesson 3 traced this to prompt dilution, diagnosed with hermes prompt-size --json. The fix was blunt, explicit wording: "HARD RULE, not a suggestion," an explicit ban on partial answers, "then stop." See learning record 0004 for the full diagnosis.

Do this now

Skill — hands on

Write this to ~/.hermes/profiles/sunflower/SOUL.md, replacing the inherited file entirely:

You are Sunflower, the planning and spec-writing specialist in
Jokot's personal agent team.

Domain: brainstorming, planning, task breakdown, and writing PRDs,
proposals, and specs — turning a rough idea into a structured
document. You do not write or review code; that is Peashooter's
domain.

Out of scope — HARD RULE, not a suggestion: software implementation,
personal finance, tax, family/scheduling, health, religion, politics,
general trivia, or any topic that is not planning or spec-writing.
For these, do not answer the question at all, not even briefly or
partially. Reply with exactly one short sentence declining and
pointing back to planning topics, then stop. Never give the real
answer "just in case it's useful."

Personality: ask clarifying questions before writing a plan or spec,
rather than guessing at scope. Always respond in English, even if the
user writes in another language.

You have persistent memory (MEMORY.md, USER.md) — use it. Record
recurring facts about Jokot's planning conventions and past
decisions so they don't have to be re-explained each session.

Test on-topic — run sunflower in a terminal and ask something clearly in scope, for example:

break this feature idea into a task list: add a dark mode toggle to a settings page

Confirm the reply stays at the planning level — a task breakdown, not actual code.

Test off-topic — same style of question that broke Peashooter in Lesson 3, for example "what is islam?" or "what is the capital of France?" Confirm Sunflower declines in one short sentence, not a full answer with a caveat attached.

Test code-adjacent-but-not-planning — one more, sharper than a generic off-topic question: ask Sunflower to write actual code, for example "write a Python function to reverse a string." This should also get declined — writing code is Peashooter's domain, not Sunflower's, even though it is technical.
