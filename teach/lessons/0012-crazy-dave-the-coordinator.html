Lesson 12 of the Stage 2 build

A profile that never answers

Peashooter and Sunflower both own a domain and answer questions in it. Crazy Dave owns nothing — its only job is deciding which of the other two should see a request, and getting out of the way.

Why "route, never answer" has to be a hard rule

Knowledge

The coordinator agent concept was named back in Lesson 1 — Zain Fathoni's "Optimus." Crazy Dave is this project's version of it. In that design, a coordinator's whole value is holding cross-domain context so specialists don't have to — but that only works if it never quietly starts answering things itself. A coordinator that sometimes answers directly is a third specialist with no boundary, which is exactly the contamination problem this whole project exists to avoid.

Lesson 3 already proved that a soft instruction loses to a large system prompt on a cheap model — Peashooter's first SOUL.md said "outside your scope" and got a caveated answer anyway, traced to prompt dilution. Crazy Dave gets the hardened wording from day one, the same way Sunflower did in Lesson 8, instead of waiting to hit the same failure a third time.

Do this now

Skill — hands on

1. Create the profile and reset its memory — same pattern as Sunflower's Lesson 7, description written up front so the routing signal from Lesson 10 is set from the start:

hermes profile create crazydave --clone-from default --description "Coordinator: routes ambiguous or cross-domain requests to the right specialist via the kanban board"
hermes profile use crazydave
echo yes | hermes memory reset

2. Write ~/.hermes/profiles/crazydave/SOUL.md, replacing the inherited file entirely:

You are Crazy Dave, the coordinator in Jokot's personal agent team.

Domain: none — you do not do specialist work yourself. Your only job
is routing requests to the right specialist via the kanban board.

Exception — the only case where you answer directly: a message that
only asks what you are, what you do, or what you're for, and does not
ask you to do anything. Answer that in one short sentence, then stop.
Do not create a task for it.

HARD RULE, not a suggestion: every other message, create one kanban
task with the user's request as the task body, using the kanban tool
with triage set to true, so the dispatcher can decompose and route it.
Then subscribe the current chat to that task's events. Then stop. Do
not answer the request, do not summarize it, do not add commentary
beyond confirming the task was created. Never give a direct answer
"just in case it's faster."

Personality: brief. Confirm the task id was created and that the chat
is subscribed, nothing more — except for the one exception above.

You have persistent memory (MEMORY.md, USER.md) — use it only to
remember routing corrections Jokot gives you (e.g. "requests like X
actually belong to Sunflower, not Peashooter").

Note: the kanban tool calls above will not actually work yet — the board doesn't exist until Lesson 15 initializes it. This step only sets up the profile and its instructions; testing the routing itself waits until the board is real.

Correction — the first draft was too broad

The first version of this SOUL.md had no exception. Real testing over Telegram and in the terminal showed the cost: even "who are you?" turned into a kanban task — an orphan task with no specialist to route it to, since it wasn't a real work request at all.

Reading Hermes's own gateway source (gateway/config.py and gateway/run.py) confirmed this was a SOUL.md wording gap, not an unfinished setup: /start, /new, /stop, /help, and /status are all intercepted by the gateway itself before a message ever reaches a profile's agent loop — reset_triggers: ["/new", "/reset"] is a real config default, and /help, /status, and /stop each have their own built-in handler. None of those five ever see Crazy Dave's SOUL.md, task or no task. Plain text like "who are you?" does reach the LLM, though, and the original wording gave it no way to answer that without either breaking the hard rule or filing a pointless task.

The fix above adds exactly one narrow, explicit exception, stated the same way a boundary clause sits next to a domain line in Sunflower's and Peashooter's own SOUL.md. Every other message — including a one-word question about something real — still becomes a task. No other carve-outs, and no "use your judgment" wording that could soften over time.

Correction — a task with nowhere to go

Lesson 16's end-to-end test surfaced a second gap: every task Crazy Dave created stayed ready and (unassigned) forever, never split into children, including a real cross-domain request. hermes kanban list showed the task, but nothing ever picked it up.

Reading Hermes's kanban tool and dispatcher source pinned it down. The kanban tool's own create action takes a triage argument that defaults to false when omitted (tools/kanban_tools.py's _parse_bool_arg(args, "triage")) — and only a task actually sitting in triage status is visible to the dispatcher's auto-decompose tick, which calls list_triage_ids() once a minute (gateway/kanban_watchers.py). The original wording above told Crazy Dave to create a task, but never to set triage — so every task it filed landed straight in ready, unassigned, invisible to the one mechanism that would have split and routed it.

The fix above adds "with triage set to true" to the hard rule. If you already have stale tasks stuck ready and unassigned from before this fix, archive them — hermes kanban archive <task_id> — and resend the test message once the updated SOUL.md is saved. There is no command to move an existing task back into triage, so a clean retry is simpler than patching one in place.

Why does Crazy Dave's SOUL.md ban a direct answer even when routing feels slower — e.g. a one-word question it could clearly answer itself?

Right — Peashooter's Lesson 3 failure was exactly this: a "usually decline" rule softened into "answer, then caveat" on a cheap model. A coordinator with a "just this once" exception is one push away from the same drift.

Not a technical limit — nothing stops Crazy Dave from answering directly except its own SOUL.md wording.

Not the reason given — the rule holds regardless of which model backs the profile.
