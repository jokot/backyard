Lesson 20 of the Stage 3 build

The rule that only knew one door

Crazy Dave's hard rule was written when Dave could hear exactly one thing: a private message from you. Lesson 19 gave it a second door, and the rule does not know that door exists.

The task named hello

Knowledge

Test 4 in Lesson 19 left a task on the board whose entire body is the word hello. Nothing malfunctioned. Crazy Dave obeyed the rule it has. The rule says every message that is not an identity question and not a worker protocol message becomes a kanban task, and a greeting in #General is neither of those.

In a private chat that rule was safe. Every message you send to a coordinator bot in its own direct chat is plausibly a request for work. A group topic carries traffic no direct chat ever carries: greetings, thanks, an acknowledgement, a question about something already running. Each one now becomes a triage task, gets decomposed, and gets dispatched to a real worker.

This is the fourth correction to one file, and learning record 0009 already named the shape: a hard rule written against one input channel breaks on the second channel. The first draft knew only work requests, so an identity question became an orphan task. The second never said triage. The third never said which sender it was answering, so the board's own dispatch became a task. This one never asked what a room sounds like.

Count the doors before you write the next clause. Crazy Dave now has three: your direct chat, the kanban dispatcher, and #General with no mention required. Whether a reply from Peashooter or Sunflower in #General is a fourth door is not settled here. Telegram normally does not deliver one bot's message to another bot. Test 3 below checks that on your own group rather than assuming it.

Why "reply when it is just conversation" is the wrong fix

Knowledge

The obvious wording is to tell Dave to answer normal conversation and file a task for real requests. That is the wording that already failed once. Lesson 12 traced Peashooter's first SOUL.md failure to prompt dilution: a rule that asks the model to judge loses to a large system prompt on a cheap model. "Is this conversation or a request?" is a judgment on every single message.

The two failures are not equally bad, and that decides the shape of the fix. A junk task is visible. It sits on the board with a body you can read, and one archive command removes it. A request that Dave answers as chat instead of filing leaves no record anywhere. You believe the work started. Nothing started. Call this silent non-routing, and treat it as the failure worth paying for.

So filing stays the default, and every reply is a named exception to it. Each exception names a moment, not a kind of message, which is the mitigation record 0009 asked for. Two moments earn a clause. Small talk stops the junk. Board questions are the capability worth having, because Dave already holds the answer and no worker does.

Do this now

Skill — hands on

1. Archive the task Lesson 19 created. Read its id from the list, then archive it:

hermes kanban list
hermes kanban archive <task_id>

2. Open ~/.hermes/profiles/crazydave/SOUL.md and add two exceptions. They go directly after the dispatched-work exception and directly before the line beginning HARD RULE:

Exception — small talk: a message that only greets, thanks, or
acknowledges, and asks for nothing. Reply in one short sentence. Do not
create a task.

Exception — board questions: a message that asks about the state of work
already on the board. Read the board with the kanban tool and answer
from what you read. Do not create a task. If the message asks about work
that is not on the board, it is a new request, and the HARD RULE
applies.

3. Change one number lower down. The personality line ends "except for the two exceptions above". There are four now:

Personality: brief. Confirm the task id was created, nothing more —
except for the four exceptions above.

4. Check the file before restarting. Four lines should come back, in this order:

grep -n 'Exception —\|HARD RULE, not a suggestion' ~/.hermes/profiles/crazydave/SOUL.md

If HARD RULE is not the last of the four, an exception landed below it. Move it up. A clause after the hard rule reads as an afterthought to the model, and the hard rule is the one that must read as the default.

5. Restart Crazy Dave only. The other two profiles did not change:

hermes gateway restart -p crazydave

6. Run four tests in #General, in this order. Run hermes kanban list after each one:

  • Post thanks. Expect one short reply and no new task. This tests the small talk clause.
  • Post what is on the board right now. Expect an answer that names real tasks and no new task. This tests the board questions clause.
  • Post @your_peashooter_bot say hello back, wait for Peashooter to reply, then wait 30 seconds. Expect no reply from Crazy Dave and no new task. This tests whether another bot's message reaches Dave at all.
  • Post write a one page spec for a habit tracker. Expect a new triage task and no direct answer. This is the regression check, and it is the one that matters most.

7. Mirror the file into the repository and commit it, the same way every earlier profile edit was mirrored:

cp ~/.hermes/profiles/crazydave/SOUL.md hermes-config/crazydave/SOUL.md
The sentence that does the work

One sentence in the second clause carries the whole safety argument: "If the message asks about work that is not on the board, it is a new request, and the HARD RULE applies."

Without it, "did you finish the habit tracker spec?" is a board question by its wording, so Dave reads the board, finds nothing, and tells you so. That is a polite, correct, useless answer, and no task exists. With it, the same message becomes a task, because the board did not have the work. The clause routes on what Dave finds, not on how you phrased the question.

Test 4 above exists for exactly this reason. If any future edit to this file makes test 4 produce a chat reply instead of a task, that edit reintroduced silent non-routing, whatever else it improved.

Why do the new clauses enumerate two named moments instead of telling Crazy Dave to reply when a message is conversational?

Right — Lesson 3 traced that failure to prompt dilution, and record 0009 asks each clause to name a moment rather than a kind of message. Judgment on every message is the drift the closed set prevents.

Not a technical limit — Dave reads the board with the same tool in a topic as in a direct chat.

Delivery speed plays no part — the gate runs before the model, and the model is not timed.
