Lesson 20 of the Stage 3 build

The rule that only knew one door

Crazy Dave's hard rule was written when Dave could hear exactly one thing: a private message from you. Lesson 19 gave it a second door, and the rule does not know that door exists.

The task named hello

Knowledge

Test 4 in Lesson 19 left a task on the board whose entire body is the word hello. Nothing malfunctioned. Crazy Dave obeyed the rule it has. The rule says every message that is not an identity question and not a worker protocol message becomes a kanban task, and a greeting in #General is neither of those.

In a private chat that rule was safe. Every message you send to a coordinator bot in its own direct chat is plausibly a request for work. A group topic carries traffic no direct chat ever carries: greetings, thanks, an acknowledgement, a question about something already running. Each one now becomes a triage task, gets decomposed, and gets dispatched to a real worker.

This is the fourth correction to one file, and learning record 0009 already named the shape: a hard rule written against one input channel breaks on the second channel. The first draft knew only work requests, so an identity question became an orphan task. The second never said triage. The third never said which sender it was answering, so the board's own dispatch became a task. This one never asked what a room sounds like.

Count the doors before you write the next clause. Crazy Dave now has three: your direct chat, the kanban dispatcher, and #General with no mention required. Whether a reply from Peashooter or Sunflower in #General is a fourth door is not settled here. Telegram normally does not deliver one bot's message to another bot. Test 4 below checks that on your own group rather than assuming it.

Why "reply when it is just conversation" is the wrong fix

Knowledge

The obvious wording is to tell Dave to answer normal conversation and file a task for real requests. That is the wording that already failed once. Lesson 12 traced Peashooter's first SOUL.md failure to prompt dilution: a rule that asks the model to judge loses to a large system prompt on a cheap model. "Is this conversation or a request?" is a judgment on every single message.

The two failures are not equally bad, and that decides the shape of the fix. A junk task is visible. It sits on the board with a body you can read, and one archive command removes it. A request that Dave answers as chat instead of filing leaves no record anywhere. You believe the work started. Nothing started. Call this silent non-routing, and treat it as the failure worth paying for.

So filing stays the default, and every reply is a named exception to it. Each exception names a moment, not a kind of message, which is the mitigation record 0009 asked for. Two moments earn a clause. Small talk stops the junk. Board questions are the capability worth having, because Dave already holds the answer and no worker does.

Do this now

Skill — hands on

1. Archive the task Lesson 19 created. Read its id from the list, then archive it:

hermes kanban list
hermes kanban archive <task_id>

2. Open ~/.hermes/profiles/crazydave/SOUL.md and add two exceptions. They go directly after the dispatched-work exception and directly before the line beginning HARD RULE:

Exception — small talk: a message that only greets, thanks, or
acknowledges, and asks for nothing. Reply in one short sentence. Do not
create a task.

Exception — board questions: a message about the board and the tasks on
it. This covers their status, their content, their assignees, what
happened inside them, how they group, and which of them look wrong. Read
the board, then answer from what you read. Give your own judgement when
the message asks for one. Do not create a task.

Two limits on this exception. The message must be about the board: a
request to build, write, fix, or plan something new is not a board
question, even when it mentions the board. Answering must change
nothing: if the message asks you to archive, edit, close, assign, or run
anything, the HARD RULE applies.

3. Change one number lower down. The personality line ends "except for the two exceptions above". There are four now:

Personality: brief. Confirm the task id was created, nothing more —
except for the four exceptions above.

4. Check the file before restarting. Four lines should come back, in this order:

grep -n 'Exception —\|HARD RULE, not a suggestion' ~/.hermes/profiles/crazydave/SOUL.md

If HARD RULE is not the last of the four, an exception landed inside the hard rule and split it in two. Move the exception above the line that begins HARD RULE. This check protects the hard rule from being cut in half. It says nothing about which clause the model obeys, and the run recorded below shows that clause order was not the deciding factor.

5. Restart Crazy Dave only. The other two profiles did not change:

hermes gateway restart -p crazydave

6. Reset the session in every chat Crazy Dave listens to. Send this one word to the Crazy Dave bot in its direct chat, and again in #General:

/new

Restarting the gateway is not enough. It rebuilds the system prompt from the new file, and it leaves the conversation history alone. That history is every earlier turn in which Crazy Dave filed a task for a message, and the model follows the transcript it can see. The correction below is the run that proved it.

7. Run five tests in #General, in this order. Run hermes kanban list after each one:

  • Post thanks. Expect one short reply and no new task. This tests the small talk clause.
  • Post what is on the board right now. Expect an answer that names real tasks and no new task. This tests the status half of the board questions clause.
  • Reply to that answer with which of those is not real engineering work. Expect a named task and a reason for the call, and no new task. This tests the judgement half of the same clause, and it is the test that fails when the clause says state instead of about.
  • Post @your_peashooter_bot say hello back, wait for Peashooter to reply, then wait 30 seconds. Expect no reply from Crazy Dave and no new task. This tests whether another bot's message reaches Dave at all.
  • Post write a one page spec for a habit tracker. Expect a new triage task and no direct answer. This is the regression check, and it is the one that matters most.

8. Mirror the file into the repository and commit it, the same way every earlier profile edit was mirrored:

cp ~/.hermes/profiles/crazydave/SOUL.md hermes-config/crazydave/SOUL.md
Correction — the edit was right and nothing changed

The first real run of this lesson failed. The two clauses were in ~/.hermes/profiles/crazydave/SOUL.md, the file was saved at 22:48, and the gateway restarted at 22:52. At 22:54 the word hi in the direct chat produced this:

hermes kanban create "Respond to greeting" --triage \
  --body "Respond appropriately to the user's greeting: hi." --json

The decomposer assigned that task to Sunflower, which spent 15 seconds writing a friendly hello. Three such tasks reached done before anyone noticed.

The prompt was not the problem. Hermes stores no system prompt with a session. It rebuilds one per turn in agent/system_prompt.py, so the 22:54 turn read the file saved at 22:48. The clauses were in front of the model, and the model filed the task anyway.

The log holds the control. At 23:04 the direct chat received /new. The #General session did not. Then, in 38 seconds:

23:05:10  #General  'heloo'          old session  2 API calls, terminal, task t_e64f9a01
23:05:24  direct    'good night'     new session  1 API call,  no tool
23:05:38  #General  /new
23:05:48  #General  'good evening'   new session  1 API call,  no tool
23:05:58  #General  'hi how are you' new session  1 API call,  no tool

Same file, same model, same minute, opposite results. The only difference is the conversation history. The old sessions carried turn after turn of Crazy Dave filing a task for whatever arrived, and the model copied its own transcript rather than the new clause above it. Call this session history precedent.

A configuration change takes effect at the next restart. A SOUL.md change takes effect at the next restart in a chat that has no history yet. Full detail in learning record 0013.

Correction — one word made the clause too narrow

The second real run failed on a question that looks like the one in test 2. The first draft of the board questions clause read "a message that asks about the state of work already on the board". Two questions in a row proved what that word costs.

23:24  'What's on the board right now?'   → hermes kanban list, answered, no task
23:26  'which one do you think it's a noise task' → task t_a8886bb1 created

The second question was a reply to Dave's own list, so every task it asked about was already on the screen. Dave filed Identify the noise task among board tasks and justify the call, gave it to Sunflower, and Sunflower completed it two minutes later. The answer arrived as a finished task instead of a sentence.

The word state is what did it. A state is a status, and a judgement about which task does not belong is not a status. Dave applied the clause correctly and the clause was too narrow. The replacement in step 2 names the subject instead of the property: a message about the board and the tasks on it, with two limits that keep the boundary mechanical.

Note what the widening does not do. It does not tell Dave to use judgement about whether to reply. It tells Dave that a judgement is a legitimate thing to be asked for about a board it can read. Full detail in learning record 0014.

The sentence that does the work

Two limits close the second clause, and they are the whole safety argument. Without the first, "write a spec for the habit tracker on the board" is a board question by its wording, so Dave answers in chat and no task exists. Without the second, "archive the noise ones" is a board question too, and Dave starts changing the board from a group chat where anyone can ask.

The two limits are mechanical, which is the point. The first asks what the message is about. The second asks whether answering changes anything outside the chat. Neither asks Dave to judge how important a request is, and neither depends on how politely you phrased it.

Test 5 above exists for exactly this reason. If any future edit to this file makes test 5 produce a chat reply instead of a task, that edit reintroduced silent non-routing, whatever else it improved.

The second limit does not survive this lesson. Lesson 21 replaces it, because "archive the noise ones" turned out to be coordinator work rather than a request for the team. The first limit stands unchanged.

Why do the new clauses enumerate two named moments instead of telling Crazy Dave to reply when a message is conversational?

Right — Lesson 3 traced that failure to prompt dilution, and record 0009 asks each clause to name a moment rather than a kind of message. Judgment on every message is the drift the closed set prevents.

Not a technical limit — Dave reads the board with the same tool in a topic as in a direct chat.

Delivery speed plays no part — the gate runs before the model, and the model is not timed.

A SOUL.md edit is saved and the gateway is restarted, yet the old behaviour continues in one chat. What explains it?

Right — a restart rebuilds the prompt and keeps every earlier turn. The model reads its own transcript as evidence of what it does, so the chat needs /new.

No cache survives a restart — Hermes stores no system prompt with a session and rebuilds one per turn.

Every turn starts a new agent after the restart, and the log shows the init on each inbound message.
