Lesson 38 · Stage 6 build

Install Hermes from the commit that the Mac runs, and prove the version

This lesson installs Hermes on the server. No profile moves, and no secret moves. All four bots continue to answer Telegram from the Mac while you work. The whole task turns on one string. When hermes --version on the server matches the Mac character for character, Task 4 can start. Lesson 37 prepared the machine. This lesson puts code on it.

Read the installer, and four questions answer themselves

Knowledge

An install invites guesses. Each guess in the next table has an answer in the repository, and each answer took one command to find:

QuestionCommandAnswer
Does the server need a key for the clone? git ls-remote <url> HEAD No. The command answers with no credentials, so the repository is public over HTTPS.
Does Ubuntu need a newer Python? sed -n '36p' setup-hermes.sh No. Line 36 reads PYTHON_VERSION="3.11", and uv downloads that version.
Does the server need node, and 545 MB of it? grep -cE 'npm|node|web/' setup-hermes.sh No. The count is 0. A tool downloads node later, and only when a tool asks for node.
Does the roster of four share one service? get_service_name() at line 1797 No. The function builds the unit name from HERMES_HOME, so four profiles give four units.

The skill in this lesson is the method, not the four answers. A question about an install has an answer in the installer. Read the file.

The installer has one branch for the operating system

Knowledge

Lines 290 to 299 of setup-hermes.sh hold the only difference between macOS and Linux:

if command -v apt &> /dev/null; then
    sudo apt install -y ripgrep && INSTALLED=true
...
if [ "$INSTALLED" = false ] && command -v brew &> /dev/null; then
    brew install ripgrep && INSTALLED=true

Task 2 installed ripgrep 14.1.0 already, so the installer finds the program and skips the branch. Nothing else in the file tests the operating system.

Reach the server as the hermes account

Skill — hands on

You run every command in this lesson on the server, as the hermes account. Open the session from the Mac:

ssh hermes-vps

The prompt changes to hermes@vps-.... Lesson 37 wrote the block for hermes-vps into ~/.ssh/config. From an open ubuntu session, the command sudo -u hermes -i reaches the same account.

Confirm the account and the home directory:

whoami
pwd

The two lines read hermes and /home/hermes. A different answer stops the lesson.

A dropped connection kills a running installer

Knowledge — protect a long command

The installer downloads about 1.1 GB, and the download takes several minutes. A closed SSH session sends SIGHUP to the installer, and a half-finished install is harder to read than a failed one.

The program tmux holds a session on the server. The server carries tmux at /usr/bin/tmux already.

Skill — start the session

Start a named session before the clone:

tmux new -s install

A green status bar appears at the bottom of the terminal, and the bar reads install at the left. You are now inside the session. Every later command in this lesson runs here.

You do not have to leave the session. Keep the window open, and watch the installer end. The program tmux protects the download from a dropped connection, and nothing more.

To leave the session and keep it running, use the key sequence Ctrl-b then d. On a Mac, Ctrl means the control key at the bottom left, and not the command key. The sequence has two parts. Hold control, tap b, then release both keys. Then tap d on its own.

This command does the same, and needs no key sequence:

tmux detach

The manual of tmux 3.4 lists detach-client (detach), so the short name is part of the program.

Knowledge — recovery only

Use the next command only after a dropped connection, and only when a session from tmux new already exists:

tmux attach -t install

The answer no sessions means that no session exists. The command tmux new -s install makes one. The command tmux attach never makes a session.

This command lists every session of the current account:

tmux ls

A session belongs to one account. A session that you start as ubuntu stays invisible to the hermes account.

Clone the commit that the Mac runs, not the newest one

Knowledge

The Mac runs commit 3e7c563d, dated 2026-07-17. The branch main has moved 27642 commits ahead of that commit, and 15403 files differ. This command reads the newest commit at any time:

git ls-remote https://github.com/NousResearch/hermes-agent.git HEAD

A fresh clone of main puts the server on newer code than the Mac. A cutover that then fails has two possible causes, the move and the 27642 commits. This plan keeps one cause.

The pinned commit is also the known-good code. All four bots run that commit on the Mac today. An upgrade to main stays possible after the move, as a separate step with its own test.

The profile state is a SQLite database with a version number. Line 143 of hermes_state.py reads SCHEMA_VERSION = 22 at the pinned commit. The same constant on main reads 30.

Hermes migrates a database forward when it opens the file. An install from main moves the four copied databases from version 22 to version 30 at the first start. The Mac keeps its own databases at version 22, because rsync copies and never moves.

Line 1858 of hermes_state.py reads if current_version < SCHEMA_VERSION, and no branch tests the opposite direction. The code of the Mac opens a version 30 database with no error. Two machines at version 22 keep the state copyable in both directions, and that property is the rollback plan.

Skill — hands on

Clone the repository:

git clone https://github.com/NousResearch/hermes-agent.git ~/.hermes/hermes-agent

Move to the clone:

cd ~/.hermes/hermes-agent

Select the commit:

git checkout 3e7c563d

The command prints a paragraph about a detached HEAD. That paragraph is normal. A detached HEAD means that the clone points at one commit and not at a branch, which is correct for a pinned install.

Read the commit that the clone now holds:

git log -1 --format='%h %ad' --date=short

The line reads 3e7c563d 2026-07-17. A different line stops the lesson. Report the line.

Run the installer

Skill — hands on

Start the installer from inside the clone:

cd ~/.hermes/hermes-agent && ./setup-hermes.sh

The installer downloads uv when uv is absent. The installer then makes a virtual environment with Python 3.11, and syncs from the lockfile with --locked. The step takes several minutes.

Read the disk after the installer ends:

du -sh ~/.hermes

The size reads about 1.1 GB. The server holds 34 GB of free space, so the install fits with room to spare.

One string decides the gate

Skill — hands on

Print the version:

~/.local/bin/hermes --version

The first line must read this string, character for character:

Hermes Agent v0.18.2 (2026.7.7.2) · upstream 3e7c563d

CAUTION: Do not continue to Task 4 with a version that differs. A different string means that the checkout did not hold. The move would then carry two changes at the same time, and a failure would have two possible causes.

The command must resolve by its short name

Knowledge

Lines 24 to 27 of /home/hermes/.profile add the private directory to the path:

if [ -d "$HOME/.local/bin" ] ; then
    PATH="$HOME/.local/bin:$PATH"
fi

The rule tests the directory. Before the install, the directory ~/.local/bin does not exist, so a login shell skips the rule. The installer makes the directory, and the next login shell then reads the rule and adds the path.

Skill — hands on

Read the path that the shell holds now:

which hermes || echo 'NOT ON PATH'

When the answer reads NOT ON PATH, start a new login shell:

exec bash -l

Then read the path again:

which hermes || echo 'NOT ON PATH'

The answer reads /home/hermes/.local/bin/hermes. When the answer still reads NOT ON PATH, write ~/.local/bin/hermes in every later command of this plan.

Prove that the machine holds no profile and no secret

Skill — hands on

Read the two paths that a profile would use:

ls ~/.hermes/profiles/ 2>/dev/null || echo 'NO PROFILES'
ls ~/.hermes/.env 2>/dev/null || echo 'NO ROOT ENV'

The two answers read NO PROFILES and NO ROOT ENV. The server now runs the same code as the Mac, and the server holds no bot, no token and no history.

Nothing can break in Telegram at this point, because no profile exists to answer Telegram. Task 4 carries the first copy.

Check your understanding

Why does this install select commit 3e7c563d instead of the branch main?

Correct. The branch main has moved far ahead of the Mac. Newer code plus a new machine gives two suspects for one failure.

Wrong. No such bug is known. The reason is the count of variables in the move, not the quality of the newer code.

Wrong. The repository is public. The command git ls-remote answers with no credentials, for main and for every other ref.

What proves that the server runs the same code as the Mac?

Correct. The string ends with upstream 3e7c563d, so the string carries the commit and the release together.

Wrong. An installer can end cleanly on the wrong commit. A clean end proves the install, not the version.

Wrong. Two different commits can hold the same count of files. Read the version string, and read every character.

Why does the Python version of Ubuntu not matter for this install?

Correct. Line 36 reads PYTHON_VERSION="3.11". The server ships Python 3.12.3, and that number has no effect.

Wrong. Hermes runs on Python. The installer makes a virtual environment, and uv puts the right version inside it.

Wrong. The server ships Python 3.12.3, not 3.11. The install works because uv ignores the version of the distribution.

Checkpoint

That page explains why line 36 of the installer decides the Python version, and why the version of Ubuntu does not. Read it with the manual page for git ls-remote, which is the command that proves a repository public.
