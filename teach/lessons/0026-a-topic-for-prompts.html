Lesson 26 of the Stage 4 build

One line decides which room it hears

Torchwood runs, and it listens in the wrong room. The clone carried the topic binding of Peashooter, so two bots now answer the same unnamed message in #Coding. This lesson gives Torchwood a room of its own, and the whole change is one line.

The number you cannot guess

Knowledge

A supergroup topic has a thread id. Telegram derives that id from the message id of the message that created the topic, not from a counter of topics. The Ark group holds three topics with the ids 1, 2 and 3, because those topics were made early and nothing else had been said. A fourth topic made today lands on whatever message id the group has reached.

So do not assume the next number. Read it.

The gateway log does not hold it either. The string thread= appears in ~/.hermes/profiles/torchwood/logs/agent.log, and it names a Python thread:

thread=Thread-6 (process_loop):6281949184

That number is a memory address, not a topic. The Telegram Web address bar is the source that answers correctly.

What the binding actually does

Knowledge

Three keys in config.yaml decide whether a bot answers, and they work in this order:

  • require_mention: true — the bot stays silent unless a message names it.
  • free_response_topics — a list of exceptions. In a topic on this list, the bot answers even when no message names it.
  • exclusive_bot_mentions: true — a message that names a different bot silences this one, even inside its own topic.

So the entry you are about to write does one thing. It names the single room where Torchwood speaks without being asked. Everywhere else it waits for its name. That is the pattern Lesson 19 established for the other three bots, and Torchwood is the fourth instance of it, not a new idea.

Do this now

Skill — hands on

1. Create the topic and admit the bot. In the Ark group:

  1. Open the topic list and create a topic named Prompts.
  2. Add the bot you created in Lesson 25 to the group.
  3. Promote that bot to administrator.

Administrator rights matter because Telegram delivers some supergroup updates only to administrators. A bot without them misses messages for reasons that never appear in a log.

2. Read the thread id. Open web.telegram.org/a/, open the Prompts topic, and read the address bar. It shows:

#-1004371805465_<N>

The number after the underscore is the thread id. Write it down. Step 3 needs it. Do not assume it is 4.

3. Replace the topic binding. Open ~/.hermes/profiles/torchwood/config.yaml and find the telegram block near line 457. The clone left it holding the topic of Peashooter:

telegram:
  reactions: false
  allowed_chats: ''
  require_mention: true
  exclusive_bot_mentions: true
  free_response_topics:
    - '-1004371805465:2'

Replace 2 with the thread id from step 2, and change nothing else:

  free_response_topics:
    - '-1004371805465:<N>'

Keep the quotation marks. A bare value that starts with a minus sign and holds a colon is ambiguous in YAML. Leave allowed_chats empty. A value there becomes a second gate that the group must also pass, and a half-filled second gate is a silence with no error message.

4. Restart the gateway.

hermes -p torchwood gateway restart
hermes -p torchwood gateway status

If status reports Gateway is not running and offers you hermes gateway install, then no service exists for this profile yet. Install it once, and use restart from then on:

hermes -p torchwood gateway install --start-now --start-on-login

Expected from status: a launchd plist path, and a line reading Gateway is supervised by launchd with a process id.

5. Run four tests, one for each topic. Post hello with no mention of any bot, and record which bots answer:

  1. Prompts — Torchwood answers, alone.
  2. #Coding — Peashooter answers, alone.
  3. #Planning — Sunflower answers, alone.
  4. #General — Crazy Dave answers, alone.

Test 1 has a second check. The reply must come from the username you created in Lesson 25. A reply from the Peashooter username means the token replacement never took effect, and two gateways are polling one bot.

Read the silence correctly

Three failures look the same from the chat window, and each has a different cause.

  • No bot answers in Prompts. Group privacy is still enabled on the new bot, so it never receives an unnamed message. Return to Lesson 25 step 1.
  • Torchwood answers in Prompts and in #Coding. The edit in step 3 did not reach the running process. Restart, then read the file again.
  • Two bots answer in Prompts. Two profiles name the same thread id. Compare all four files before you state a cause.
for p in crazydave peashooter sunflower torchwood; do
  echo "--- $p"
  grep -A2 free_response_topics ~/.hermes/profiles/$p/config.yaml
done

Expected: four different thread ids, one for each profile.

You create the fourth topic in a group that already holds topics 1, 2 and 3, and you write 4 in the configuration file without checking. Torchwood stays silent in the new topic. Why?

Right. A thread id is the message id of the topic creation message. The group has carried traffic since topic 3, so the fourth topic lands far above 4. The address bar holds the real number.

Quoting matters, and it is not this. A wrong number and a right number both load. The file parses either way, and the bot then waits in a room that holds nobody.

A restart is required, and it repairs nothing here. Restart a gateway that holds the wrong thread id, and it listens to the wrong thread id faster.

Checkpoint

Torchwood now owns a room, and it still answers in the voice of Peashooter, because SOUL.md arrived with the clone. Lesson 27 deals with the next carry-over: the routing description that still offers Torchwood as a place to send engineering work.

Primary source: the Telegram Bot API page on forum topics, and your own ~/.hermes/profiles/torchwood/config.yaml. Read the second one first. It is the file the running gateway actually reads, and it matches the version you are running.
