A soul file states one command, and the script holds the steps

Three soul files call hermes send --to telegram on their own, and skip the new report script from Lesson 32. Fizzy never receives a comment when that call runs alone, because only the report script resolves a card. This lesson replaces four lines and removes one, across three files. It adds a note to each file. It also adds the delivery step that lets a live chat see the change.

Knowledge

Each file names itself, and the file says why

Skill — hands on

A soul file is the only place an agent reads the call, so the file must also carry the reason for the first word. Lesson 32 holds the full account: a worker shell carries no profile marker, and hermes send with no --profile flag reads the machine wide file ~/.hermes/active_profile instead.

Add these four lines to all three files, beside the command that you just edited. Change no word of them:

The first word is your own name, and it never changes. The script
sends under that name, because a terminal carries no record of which
agent called it. Drop the name and the script exits 2 and sends
nothing.

Put the note after the command block in Peashooter and in Sunflower. Put it before the sentence Write a short summary of the whole job in your own voice. in Crazy Dave.

The note tells the agent what to do when the rule and the moment disagree. An agent that reads "use your own name" writes its own name. An agent that reads only an example line copies the example.

A tilde is not a path yet

Knowledge

Every call above writes the path in full. The first version of these three files wrote ~/.hermes/scripts/hermes-report.sh, and that version blocked. A terminal expands the tilde before the command runs, so the same line works when you type it. An agent does not get that far.

The security scanner reads a command before the agent runs it. When the command names a script, the scanner opens that script and reads the body too, because a safe-looking call can hold an unsafe body. A string that starts with ~ is not a path yet, so the scanner cannot open the file. It does not guess. It answers block, with two findings that both read analysis_incomplete:

Nested executable body could not be resolved
nested command analysis was incomplete

The same four calls, tested against the scanner that the profiles actually run:

Written asAnswer
~/.hermes/scripts/hermes-report.shblock
$HOME/.hermes/scripts/hermes-report.shblock
/Users/jokot/.hermes/scripts/hermes-report.shallow
bash /Users/jokot/.hermes/scripts/hermes-report.shallow

The scanner is not one program. Each profile carries its own copy under ~/.hermes/profiles/<name>/bin/, and the versions differ. The copy on your shell path, if you have one, is not the copy that judged the command. To test a rule, find the binary that the agent runs, not the binary that your shell finds.

A refused report looks like a finished report

Knowledge

The first real job of the roster lost one report of three. Crazy Dave ran the correct command, with the correct profile name, and the tool answered:

{"exit_code": -1, "status": "pending_approval",
 "approval_pending": true,
 "description": "Security scan - [HIGH] Nested executable body ..."}

That answer is neither a success nor an error. No text reached standard error, and no exit code said "failed". A machine asked a question, and nobody answered it. Crazy Dave completed the task four seconds later.

Sunflower and Peashooter met the same answer in the same job. Both read it as a failure and both sent their report a second time. The difference was not the command and not the script. The difference was the reading of one result.

A soul file can close that gap, because a soul file is where an agent learns what a result means. Record 0051 holds the full account.

Skill — hands on

Add this rule to all three files, directly after the four-line note that you just added. Change no word of it:

A report that does not send is retried - HARD RULE. A successful call
prints nothing and exits 0. Any other result means that Jokot heard
nothing. These three results are all failures:

  - A non-zero exit code.
  - Any line on standard error.
  - An approval prompt. That result carries exit code -1 and the status
    pending_approval, and it carries no error text at all.

On any of the three, run the exact same command a second time. If the
second call also fails, add a kanban comment on your task with the full
report text and the words "telegram report failed", then complete the
task. Never treat a task as reported until one call exits 0.

The fallback uses the kanban comment on purpose. That path worked in the same turn where the report failed, so the report reaches the board even when it reaches no room. A lost report is a lost task.

One command proves that all three files carry the rule:

grep -c 'HARD RULE. A successful call' \
  ~/.hermes/profiles/{crazydave,peashooter,sunflower}/SOUL.md

Each of the three lines must end with 1. A soul file edit reaches no running session, so send /new in each topic afterwards.

Prove the files, then prove the sessions

Skill — hands on

Two commands prove the edit landed, one for the files and one for the live sessions. The file proof is success criterion 4 of the spec.

grep -c 'hermes send --to telegram' ~/.hermes/profiles/*/SOUL.md

A second grep proves that each file names itself. Read the first word after the script path on every line.

grep -n 'hermes-report.sh' ~/.hermes/profiles/*/SOUL.md

Peashooter prints one line, and that line reads peashooter. Sunflower prints one line, and that line reads sunflower. Crazy Dave prints two lines, and both read crazydave. A line that names another profile sends every report of that agent under the wrong bot.

It prints one <path>:<count> line for each of the four profiles. Every count must read 0 after your edit. Torchwood already reads 0 today, because that file holds no such line.

The file proof shows the rule on disk. This second command shows the rule inside a live chat.

for p in peashooter sunflower crazydave; do
  printf '%-11s ' "$p"
  sqlite3 -readonly ~/.hermes/profiles/$p/state.db \
    "SELECT COUNT(*) FROM sessions WHERE source='telegram' AND ended_at IS NULL
       AND system_prompt LIKE '%hermes-report.sh%';"
done

A count of 1 or more means the new rule is live for that profile. A count of 0 means either the chat still runs the old prompt, or nobody sent a message after /new. Read the system_prompt column to separate the two cases, because /new leaves it NULL until the first turn.
