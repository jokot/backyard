Lesson 16 of the Stage 2 build

One message, the whole route

Lessons 7 through 15 built five separate pieces: Sunflower, Crazy Dave, both Telegram doors, and the shared board. This lesson sends one real request through all five at once and checks every hop, the same way Lesson 6 closed out Stage 1.

What "working" means here

Knowledge

Four checks close Stage 2, straight from the design spec:

  1. Sunflower answers a direct, on-topic Telegram message in character, and declines an off-topic one — Peashooter's Stage 1 checks, repeated for Sunflower.
  2. A message to Crazy Dave produces a kanban task, never a direct answer.
  3. A cross-domain request produces two linked child tasks, assigned to Sunflower and Peashooter, not left unassigned or sent to the wrong profile.
  4. One full run completes end to end — created, dispatched, worked, and reported back to the Crazy Dave chat — with no hermes kanban command run by hand during the run itself.

Checks 1 and 2 you already have evidence for, from Lessons 11 and the retest after Lesson 12's correction. This lesson is built around checks 3 and 4, the two that need every piece working together at once.

Worth knowing, not a contradiction

Check 2 above reads "never a direct answer" — written before Lesson 12's correction added one narrow exception for self-identity questions. That exception still holds: it only fires for "what are you" style questions, never for a real request like the one this lesson sends. Check 2 is really checking that a real request always becomes a task, and the exception was never in tension with that.

Do this now

Skill — hands on

1. Message Crazy Dave's Telegram bot with one request spanning both specialists — for example:

Write a short spec for a small feature, then implement it.

Report Crazy Dave's reply. It should confirm a task id and a subscribed chat, nothing more.

2. Check the board split the work:

hermes kanban list

Report the output. Expect two child tasks — one assigned sunflower, one assigned peashooter — with the implementation task depending on the spec task.

3. Inspect either child task directly:

hermes kanban show <task_id>

4. Wait, watch the Telegram chat, don't intervene. Don't run any hermes kanban command to move things along — the dispatcher does that on its own 60-second tick. Report when the Crazy Dave chat receives a completion message for each child task.

If any step doesn't match what's expected — Crazy Dave answers directly, a child task is unassigned or misrouted, or nothing ever completes — say what you saw. That's a real bug to diagnose and fix, not something to route around, the same way every bug in Stage 1 got a fix and a learning record instead of a workaround.

Correction — silence is not progress

The first real run of this lesson found the largest bug in the project so far. decompose split the request into three children correctly, Sunflower finished its spec task, and Peashooter then hit a GitHub credential no automation can mint and marked its own task blocked. Telegram stayed quiet. The only way to find out was to run hermes kanban list by hand.

Three defects stack up to produce that silence, each confirmed in Hermes's source. First, decompose never subscribes the children it creates — _maybe_auto_subscribe (tools/kanban_tools.py) runs only on the kanban_create path, so only the root task Crazy Dave files gets a subscription. Second, a blocked child never propagates status to its parent: recompute_ready (hermes_cli/kanban_db.py) promotes a task only when every parent is done or archived, so a blocked parent leaves the root sitting in todo with no event to report.

Third, and worst, the notifier has two gates that reject opposite values. Gate one (gateway/kanban_watchers.py) compares the subscription's stored profile name against the gateway's own name and skips on a mismatch. Gate two, _authorization_adapter (gateway/authz_mixin.py), treats any name other than default as a multiplex profile and fails closed when a single-profile gateway has no registry entry. So crazydave passes gate one and fails gate two, while default fails gate one. No profile name satisfies both. The notifier claimed each event and rewound the cursor every 5 seconds forever, which is why every subscription still read last_event_id = 0 hours later.

The fix is a NULL notifier_profile — the only value that passes both gates. The CLI cannot write it, so it needs a direct update:

sqlite3 ~/.hermes/kanban.db "UPDATE kanban_notify_subs SET notifier_profile = NULL WHERE platform = 'telegram';"

Accept one side effect: with NULL every gateway treats the row as its own, and whichever claims the event first sends it. Exactly one message arrives, but the sending bot is a race — in the confirming test Peashooter's bot delivered a notification for a task subscribed through Crazy Dave. Full detail in learning record 0008.

Skill — subscribe the children by hand

Until decompose subscribes its own children, do it yourself after every fan-out. Run hermes kanban list, then for each child id:

hermes kanban notify-subscribe <task_id> --platform telegram --chat-id <your_chat_id>
sqlite3 ~/.hermes/kanban.db "UPDATE kanban_notify_subs SET notifier_profile = NULL WHERE platform = 'telegram';"

One debugging note that cost real time: setting logging.level: DEBUG does nothing for gateway.log, which carries a hardcoded level=logging.INFO in hermes_logging.py. Only agent.log honors the configured level. Read ~/.hermes/profiles/<name>/logs/agent.log when you need notifier detail.
