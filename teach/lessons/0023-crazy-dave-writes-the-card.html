Lesson 23 of the Stage 3 build

A fourth rule on a file corrected three times

Crazy Dave's SOUL.md has been wrong three times, and all three failures had the same shape. This lesson adds a fourth rule to that file. Before writing it, look at why the first three broke — because the wording that avoids the pattern is not the obvious one.

The shape that keeps recurring

Knowledge

Read learning record 0009 and the three corrections in Lesson 12. The pattern:

  • Draft 1 said every message becomes a task. "Who are you?" became an orphan task.
  • Draft 2 never said triage. Every task landed unreachable by the dispatcher.
  • Draft 3 never said which sender it was answering. The kanban dispatcher became a second sender, and Crazy Dave filed tasks about its own dispatched work.

The generalization in record 0009 is that a hard rule written against one input channel breaks on the second channel. Each draft was written while one sender existed, and each broke when a second appeared.

So the mitigation for this lesson's rule is in its grammar. Each new clause names the moment it applies to, not the message that arrived. "On filing a root task" and "on completing a root task" are moments, and a moment does not care which sender caused it. "Every message" is a sender claim, and that is the phrasing that has failed three times.

Why the coordinator, and not the workers

Knowledge

Crazy Dave already runs at exactly the two moments the mirror needs, and no other profile runs at either. It files the root task when you ask for something. And because Lesson 15 set orchestrator_profile: 'crazydave', the dispatcher spawns Crazy Dave on the root task once the children finish.

Giving Peashooter and Sunflower their own Fizzy tokens would add two credentials, two failure paths, and per-child cards you do not need — the specialists already report to you directly over Telegram, from Lesson 17. One card per root task, written by one agent, is the smaller thing that still works.

Do this now

Skill — hands on

1. Add this block to ~/.hermes/profiles/crazydave/SOUL.md, after the dispatched-work exception and before the personality line. Substitute your real board id from Lesson 22. The command forms below are the ones Lesson 22 confirmed against the tool, so change nothing else:

Fizzy mirror — you own it, and you never read it.

On filing a root kanban task: after the task exists, run
  fizzy card create --profile crazydave --board <BOARD_ID> --title "<the user's request, one line>" --jq '.data.number'
That prints one integer, which is the card number. Add a comment on the
kanban task with the exact text fizzy:<number> and nothing else.

On completing a root kanban task: read the fizzy:<number> comment from
that task. Then run
  fizzy comment create --profile crazydave --card <number> --body "<your summary>"
  fizzy card close <number> --profile crazydave

Use the card number in both commands, never the 25 character card id.
The number is a flag on the first command and a positional argument on
the second.

Never run any other fizzy command. Never read a Fizzy card to decide
anything. The kanban board is the only source of truth.

If a fizzy command fails, say so in your reply and continue. A failed
fizzy command never blocks the kanban task and never changes what you
do next.

2. Check the paste landed whole.

grep -n 'fizzy' ~/.hermes/profiles/crazydave/SOUL.md

Four command lines must appear: fizzy card create, fizzy comment create, fizzy card close, and the fizzy: comment text. A missing line means a truncated paste, which is the most common cause of a rule that half-works.

3. Restart Crazy Dave's gateway so the new SOUL.md loads:

hermes gateway restart -p crazydave

4. Reset the session in every chat Crazy Dave listens to. Send /new in the direct chat and again in #General:

/new

The restart alone leaves the old history in place, and the model follows the transcript it can see. Lesson 20 records the run that proved this, and learning record 0013 holds the log.

5. Test one moment, not both. Send a small request in #General — something like write a haiku about file descriptors. Then verify the filing half from real output rather than from Crazy Dave's reply:

hermes kanban list
hermes kanban show <task_id>
fizzy card list --profile crazydave --board <BOARD_ID>

hermes kanban show must contain the fizzy: comment. fizzy card list must contain one card with the same title. The closing half gets tested in Lesson 24, because it needs a root task with finished children.

6. Mirror the file into the repository.

cp ~/.hermes/profiles/crazydave/SOUL.md hermes-config/crazydave/SOUL.md
Why the failure clause is there

The last four lines of the block look like defensive padding. They are the most important part of it.

Without them, a Fizzy outage, an expired token, or a spent free tier turns into a coordinator that will not file kanban tasks — the mirror taking down the thing it was supposed to reflect. The clause states the priority order explicitly, so an agent under pressure to "complete the instructions" has a written answer about which half to drop.

This is the same lesson as the one-way rule in Lesson 22, applied to time rather than to data. Keep every failure inside the display.

The new rules say "on filing a root task" rather than "when you receive a request". Why does that phrasing matter?

Right. Record 0009's failure was a rule written about a sender, broken when a second sender appeared. A rule keyed to an action Crazy Dave takes is unaffected by who asked.

Prompt dilution is a real risk on this profile — record 0004 covers it — but both phrasings are the same length. The difference is what they key on.

The tool does not read SOUL.md at all. The wording only ever affects how the model behaves.
