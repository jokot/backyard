Lesson 39 · Stage 6 build

Stop four bots, copy the state, and start them in an order that three facts decide

This lesson runs the cutover. All four bots stop, the state moves, and the four bots start again on the server. The order of the steps is not a preference. Three measured facts fix the order, and a step out of order costs either the board, the last few messages, or a wrong alarm. Lesson 38 put the code on the server. This lesson puts the memory on it.

One file decides the shape of the window

Knowledge — why the bots cannot move one at a time

The board is one SQLite file at ~/.hermes/kanban.db. The file holds 90 rows in the table tasks. Hermes reads the file from the disk, and offers no remote path to it.

Three bots own rows. peashooter owns 40 rows, sunflower owns 23 and crazydave owns 21. Six rows have no owner.

Two machines cannot share one such file. A bot on the Mac writes to the copy of the Mac. A bot on the server writes to the copy of the server. Each copy then holds work that the other copy never sees, and no command merges two divergent boards.

CAUTION: Do not run one board bot on the server while another board bot runs on the Mac. The split starts with the first write, and one minute is enough. The same rule holds during a rollback, so the three board bots roll back together or not at all.

torchwood goes first, because torchwood owns nothing

Knowledge — the pilot and the gate

torchwood owns 0 of the 90 rows. A failure of torchwood on the server costs no board work, so torchwood is the safe bot to start first.

torchwood is also the gate. The bot must reply in Telegram, and the reply must show history. torchwood carries 290 messages, so a question about its own recent work has a right answer.

A reply alone proves nothing. A bot with an empty state.db still replies, and gateway status still reads running. The memory is the test.

When torchwood fails the gate, stop torchwood on the server and start torchwood on the Mac. The other three bots have not moved, so the board is still whole.

Stop before you copy

Knowledge — the write-ahead log holds the newest rows

Every database in the roster runs in write-ahead log mode. PRAGMA journal_mode reads wal for kanban.db, for state.db, and for the state.db of each profile.

In that mode a new row lands in the sidecar file <name>-wal first. The main .db file gets the row later, at a checkpoint. A copy of the .db file alone therefore drops the newest writes, and drops them with no error message.

Measured on 2026-09-25 with a test database. One row was written and committed. The sidecar file then held 4152 bytes, a copy of the .db file read 0 rows, and the original read 1 row.

A gateway writes a message the moment a person sends one. So the four gateways stop first, and the checkpoint runs after the stop.

Skill — hands on

Stop all four gateways together:

for p in crazydave peashooter sunflower torchwood; do
  hermes -p "$p" gateway stop
done

Confirm that all four read stopped:

hermes gateway list

The window starts at that line. Now move every pending write into the main files:

for db in ~/.hermes/state.db ~/.hermes/kanban.db \
          ~/.hermes/profiles/*/state.db ~/.hermes/profiles/*/projects.db; do
  [ -f "$db" ] && sqlite3 "$db" 'PRAGMA wal_checkpoint(TRUNCATE);'
done

The test [ -f "$db" ] is required. sunflower has no projects.db, and sqlite3 makes an empty database at a path that it cannot find.

Copy, then rewrite, then start

Knowledge — why the rewrite comes before the start

Three soul files name the Mac in a full path. crazydave holds two references at lines 24 and 97, peashooter holds one at line 23, and sunflower holds one at line 25. torchwood needs no rewrite.

The order of the three actions matters. An edit to a soul file makes every running session of that bot report prompt-drift, and the reports continue until the gateway restarts.

Record 0053 holds the evidence. An edit to four soul file lines produced seven audit findings, and three of the seven read prompt-drift. The sessions carried dates from six days before the edit, so the findings looked older than their cause. A revert cleared all seven.

A rewrite after the start would therefore raise a real alarm about an edit that you made on purpose. Copy first, rewrite second, and start third.

The shell decides whether an exclude works

Knowledge — zsh keeps a variable in one piece

The copy carries eleven --exclude options. A reader of bash puts those options in a plain string, because bash splits an unquoted variable into words at each space.

zsh does not split an unquoted variable. The Mac runs zsh, so a plain string reaches rsync as one long argument. rsync then matches no path against it and honors none of the eleven rules.

Measured on 2026-09-25: the payload is 109 MB with the excludes and 370 MB without them. The four profiles hold 357 MB, the excluded paths hold 261 MB, and the root payload holds 17 MB.

The 261 MB is useless on the server. The command file reads Mach-O 64-bit executable arm64 for a binary in bin, and 232 MB of the total carries that same format.

Hold the options in an array:

EX=(--exclude='bin/' --exclude='lsp/' --exclude='logs/')

Then expand the array in quotes at each use:

rsync -av -e ssh "${EX[@]}" SOURCE DEST

The form "${EX[@]}" gives rsync one argument for each element. The full list of eleven options is in Step 5 of Task 5.

An accidental overlap repairs itself

Knowledge — what two gateways on one token cost

Two gateways on one bot token make Telegram answer 409 to the second one. Hermes expects the answer. Line 1312 of plugins/platforms/telegram/adapter.py defines _looks_like_polling_conflict, and line 2295 calls it.

Line 2296 logs gateway polling bootstrap conflict; gateway stays alive while conflict retry runs. The gateway keeps running and retries.

So a bot started in the wrong order costs a delay in its replies, and not a crash. The board is the thing that a wrong order damages, and the board has no such repair.

The order, in one list

Knowledge — each step and the fact behind it
  1. Stop all four gateways. One board file has no remote path.
  2. Checkpoint every database. A hot write-ahead log holds the newest rows.
  3. Take the manifest on the Mac. The manifest is the number that Gate A compares.
  4. Copy with the excludes in an array. zsh keeps an unquoted variable in one piece.
  5. Run Gate A. A failed copy is free to roll back, because no bot has started.
  6. Rewrite the four paths. An edit under a running bot reports drift.
  7. Start torchwood, and gate on it. torchwood owns 0 rows.
  8. Start the other three, one at a time. The three roll back together.

The window closes when sunflower answers.

Check your understanding

Why do the three board bots move in one window?

Correct. kanban.db holds 90 rows and sits on one disk. A bot on each machine writes to a different copy, and no command merges two.

Wrong. Each bot holds its own token in its own profile. A shared token would give 409, and Hermes retries after a 409.

Wrong. crazydave owns both cron jobs. A stopped gateway runs no cron scheduler, so the jobs wait and cost nothing.

Which bot starts first on the server, and for what reason?

Correct. A failure of torchwood costs no board work. The other three bots stay on the Mac until torchwood passes Gate B.

Wrong. crazydave owns 21 rows of the board, so a failure of crazydave is expensive. crazydave starts after the gate passes.

Wrong. sunflower owns 23 rows, which is more than the 21 rows of crazydave. sunflower starts last.

What does PRAGMA wal_checkpoint(TRUNCATE) do before the copy?

Correct. A test on 2026-09-25 held 4152 bytes in a sidecar file. A copy of the main file alone read 0 rows, and the original read 1 row.

Wrong. The gateways already stopped, so no writer is left. A lock would also end with the command.

Wrong. The command deletes no row. The word TRUNCATE names the sidecar file, which drops to zero length.
